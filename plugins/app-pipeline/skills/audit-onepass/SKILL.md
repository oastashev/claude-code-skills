# /audit-onepass — аудит документации за один проход

Задача та же, что у `app-pipeline:audit`: ответить, можно ли по этим документам запустить `/kickoff` и отдать проект Claude Code так, чтобы разработка не упёрлась в отсутствующее решение на второй день. Отличие — в порядке работы. Обычный аудит читает документы и находит то, что заметил читающий; этот сначала считает, потом симулирует исполнение и только потом читает. Так ловятся дефекты, которые чтением не ловятся: поле, которого нет в контракте; сигнатура против вызова; значение словаря без обработчика; Must, достижимый только через Should; два требования на один вход с разным исходом; счётчик в прозе против таблицы; ссылка, устаревшая после разбиения требования.

Аудит ничего не придумывает и не переписывает документы без разрешения. Результат — `docs/06-audit-report.md` с вердиктом, результатами батареи и списком находок.

## Правило остановки

После отчёта (и, если пользователь согласился, исправления Minor) шаг закончен. Не запускай `/kickoff`, не пересобирай документы с крупными проблемами сам — для этого есть `/assemble <DOC>` и `/explore`, и решение о пересборке принимает пользователь.

## Как задавать вопросы

Любой вопрос — только через `AskUserQuestion`, 2–4 конкретных варианта, рекомендуемый первым с пометкой «(Recommended)». Вопрос обычным текстом — нарушение.

## Где живут файлы

Подключённая папка проекта (`docs/`, при наличии — `openspec/`) → `AskUserQuestion` «Подключу папку сейчас (Recommended)» / «Работать в документах Project» → документы claude.ai Project под теми же путями (`project_read` / `project_write`) + `SendUserFile`. Состояние — `docs/STATUS.md`. В режиме Project-документов `openspec/`, `AGENTS.md` и `CLAUDE.md` недоступны — скажи об этом в отчёте, а не пропускай молча. Батарея требует файлов на диске: в режиме Project сначала выгрузи документы во временный каталог и гоняй скрипты по нему.

## Порядок одного прохода

Порядок обязателен: каждый следующий шаг работает на фактах предыдущего.

1. **Батарея** (машина, 1–2 минуты). Прогнать `audit_checks.py` по `docs/`. Получить список упавших проверок и кандидатов.
2. **Индекс** (машина). `audit_index.py --json` даёт требования, носителей, контракты, словари, вызовы, символы и числовые утверждения. Этот индекс — вход для шагов 3 и 4: субагентам он передаётся как факты, чтобы они не пересчитывали то, что уже посчитано, и не спорили с арифметикой.
3. **Сквозные прогоны** (модель, сам аудитор). Пройти документы как исполнитель по 6–8 сценариям (ниже). Это единственный способ поймать «шаг не определён» и «решение принимают два места разными словами» — батарея такое не видит.
4. **Чтение по чек-листам** (субагенты, параллельно). По одному на документ или группу; каждому — пути к файлам, чек-лист и индекс; своих выводов не передавать, чтобы получить независимый взгляд.
5. **Сведение и подтверждение** (сам аудитор). Каждый Blocker и Major подтвердить дословной цитатой из документа. Неподтверждённое в отчёт не идёт. Кандидаты батареи, не ставшие находками, перечислить в §2 отчёта как проверенные и снятые.

## Батарея проверок

Скрипты лежат рядом со скилом в `scripts/`. При первом запуске в проекте скопируй их в `docs/.audit/` — оттуда их сможет гонять и `/assemble` после каждого блока правок, и пользователь руками:

```bash
mkdir -p docs/.audit && cp <skill>/scripts/audit_*.py docs/.audit/
python3 docs/.audit/audit_checks.py --docs docs --json docs/.audit/findings.json
python3 docs/.audit/audit_index.py  --docs docs --json docs/.audit/index.json
```

Если каталога со скриптами нет (скил установлен без файлов) — напиши их заново по спецификации ниже; важен состав проверок, а не конкретный код. Скрипты рассчитаны на документы по шаблонам `/assemble`: таблицы с колонкой `ID`, требования с колонками `EARS statement (en) | Пояснение | Приоритет | Источник | Сценарии приёмки`, объявления типов в блоках ```ts, журналы изменений строками `| версия | дата | …`.

| Проверка | Что считает | Что ловит |
|---|---|---|
| C-01 | Замкнутость `BR → FR/NFR → C → M → CH → T` в обе стороны, требования в двух changes, задачи без требований | Разорванную трассируемость, осиротевшие задачи |
| C-02 | Версии в шапках «Основан на», строки STATUS, сортировку журналов, равенство последней строки журнала версии в шапке | Устаревшие шапки, несортированные журналы — классический хвост после правок |
| C-03 | Матрицу BR → требования против колонки «Источник» в обе стороны | Разошедшуюся матрицу |
| C-04 | Механику EARS: ровно один `SHALL`, один шаблон, слова-маркеры, приоритет, источник, непустой сценарий | Формальные дефекты требований; даёт метрику «доля прошедших» |
| C-05 | Символы контрактной формы (snake_case и точечные ключи), использованные, но не объявленные ни в одном контракте или таблице ключей | Поля и ключи без антецедента — после переезда в OpenSpec ссылка повиснет |
| C-06 | Счётчик ключей в сценарии против состава в формулировке; обращения `x.field` в псевдокоде против объявленных типов | Поле, которого нет в контракте; «ровно N ключей» против перечня |
| C-07 | Закрытые словари: объявленное число значений против перечисленного; у каждого значения — требование, которое его ставит | Мёртвое значение словаря; значение без обработчика или без снятия |
| C-08 | Сигнатуры функций из блоков ```ts против вызовов в прозе алгоритмов: арность | Вызов, который не соберётся: не тот набор аргументов |
| C-09 | Must-требования, чьи формулировка и сценарии ссылаются только на Should | Must, достижимый только через необязательное |
| C-10 | Кластеры требований с одинаковым нормализованным триггером и разными исходами; триггер как частный случай другого | Два требования на один вход с разным исходом |
| C-11 | Числа в формулировке против чисел в сценариях | Сценарий не достигает объявленной границы |
| C-12 | Числовые утверждения в прозе («девятнадцать требований CH-00») против пересчёта по таблицам | Счётчик, отставший после правки |
| C-13 | Ссылки вида «FR-nnn „цитата“» против фактического текста требования | Ссылку, устаревшую после разбиения или переформулировки |
| C-14 | Распределение по changes, теги задач, обещания автоархивации | Противоречие «change архивируется сам» против задачи, которую никто не закрывает |
| C-15 | Триггеры `WHEN`/`IF`/`WHILE`/`WHERE`, опирающиеся на производное состояние (класс, окно, фазу, вердикт, событие — то, что система вычисляет сама), у которого нет требования-производителя | Требование без входа: Must, который не сработает никогда |

Правило чтения результатов: **упавшая проверка — кандидат, а не находка.** C-05, C-10, C-11 и C-15 по устройству дают ложные срабатывания (намеренно разбитые требования, прозаические сокращения, символы из внешних API, внешние триггеры — действие человека, ответ внешней системы, факт из git). Находкой кандидат становится после того, как ты подтвердил его дословной цитатой. Обратное тоже верно: зелёная батарея не значит «блокеров нет» — она не видит замысла, поэтому шаги 3 и 4 обязательны.

## Сквозные прогоны

Выведи 6–8 сценариев из типа системы и пройди по ним документы как исполнитель: шаг за шагом, отмечая для каждого шага, каким ID он определён и чего не хватает. Для систем с внешними вызовами (агенты, процессы, API) минимальный набор:

1. Счастливый путь целиком, от входа до завершения.
2. Внешний вызов вернул ненулевой код возврата.
3. Внешний вызов завис и убит по таймауту.
4. Внешний вызов вернул мусор или частичный результат.
5. Ресурс занят или конфликт при записи.
6. Внешний лимит исчерпан (квота, rate limit).
7. Человек вмешался посреди работы (повтор, пропуск, остановка).
8. Процесс убит посреди этапа, следующий запуск подбирает состояние.

Формат прогона — таблица: `шаг → чем определён (ID) → что неизвестно`. Правило уровня: шаг, для которого следующее действие не определено ни одним требованием и ни одним разделом дизайна, — **Blocker**, если он лежит на пути первых трёх changes, и **Major** в остальных случаях. Отдельно отмечай шаги, где решение принимают два места разными словами: это Blocker независимо от change, потому что два исполнителя напишут разный код.

В отчёт идут и прогоны, где всё определено: они показывают, что проверка была полной.

## Чтение по чек-листам

Субагенты читают параллельно; каждому — пути, чек-лист и `index.json`. Сводит и выносит вердикт аудитор.

**Полнота документов.** Сверь с шаблонами `/assemble`: exploration — направление, карта capabilities с ID, non-goals; BRD — измеримые KPI, MoSCoW у всех BR, критерии приёмки, не опирающиеся на требования более низкого приоритета и не ссылающиеся вниз на детальный дизайн; TRD — каждая CAP покрыта FR, NFR по всем категориям либо явное «не применимо, потому что…», требования к данным и ПДн, словарь ключей конфигурации; SAD — ADR-01 с Clean Architecture и привязкой слоёв к компонентам, ADR на каждый нетривиальный выбор, линтер и форматтер, таблица «NFR → как обеспечивается → как проверяется» на все NFR, целевое окружение walking skeleton и путь доставки; SDD — реестр IF-xx с привязкой к модулям и FR (полные контракты в DDD §4, не продублированы), модель данных с инвариантами, граничные случаи, стратегия тестирования; DDD — план changes с нулевым walking skeleton и каркасом, детальный дизайн модулей, контракты и задачи с критериями для CH-00–CH-02, структура репозитория по слоям, DoD, соглашения для AGENTS.md.

**Согласованность.** Противоречия между документами (стек, границы MVP, значения NFR); терминология; дублирование — дубль Minor, разошедшийся дубль Major. Особое внимание к контрактам, повторённым в трёх местах (состав записи, колонки файла, словари): они расходятся первыми.

**Готовность к OpenSpec и Claude Code.** Имена capabilities в kebab-case; требования нулевого change попадают в спецификации (проверь, записано ли, как именно); зависимости changes без цикла; каждое Must/Should ровно в одном change; задачи CH-00–CH-02 выполнимы за сессию и имеют критерий; есть всё для AGENTS.md; Must-требования без `[TBD]`; открытые Q-xx со сроком «/kickoff» или раньше закрыты.

Если существует `docs/07-kickoff.md` — волны: волна каждого change больше волны любой зависимости, внутри волны модули не пересекаются, волны 0 и 1 содержат только нулевой и первый change, числа анализа параллелизма пересчитываются из таблицы. Если существует `openspec/` — формат `### Requirement:` / `#### Scenario:`, `## Purpose` у новых capabilities, `openspec/config.yaml` парсится, каждое Must/Should встречается ровно в одном change; при наличии CLI запусти `openspec validate --all --strict` и включи вывод в отчёт.

## Таксономия дефектов → уровень

Уровень ставится по типу дефекта, а не по ощущению — иначе он плавает между кругами.

**Blocker.** Требование или шаг алгоритма неисполним: нет поля в контракте, нет сигнатуры, нет правила для входа. Два требования на один вход с разным исходом. Must-результат достижим только через Should, и он на горячем пути первых трёх changes. Шаг алгоритма не определён. Требования change не попадают в спецификации. Нет документа или он в статусе `draft`/`stale`.

**Major.** Разошедшийся дубль контракта. Устаревшая ссылка или счётчик, по которому пишут артефакт. Носитель требования назван неверно или не назван. Сценарий не проверяет своё требование или не достигает объявленной границы. Диаграмма противоречит тексту. Устаревшая шапка, несортированный журнал. Must через Should вне горячего пути.

**Minor.** Формулировка, пояснение, ссылка на не тот раздел, мёртвое значение словаря, стиль, опечатка в ID, отсутствующая строка в матрице.

Вердикт: **READY** — нет Blocker и Major; **READY WITH CONDITIONS** — нет Blocker, есть Major, которые можно закрыть до конца каркаса или не затрагивают CH-00–CH-02, условия перечислены явно; **NOT READY** — есть хотя бы один Blocker.

## Отчёт `docs/06-audit-report.md`

```markdown
# Audit report: <название проекта>
Версия: N · Дата: YYYY-MM-DD · Проверенные версии: exploration v1, BRD v2, TRD v1, SAD v1, SDD v1, DDD v1

## 1. Вердикт
READY | READY WITH CONDITIONS | NOT READY — одним абзацем почему, с перечнем блокеров одной строкой каждый.

## 2. Батарея проверок
| Проверка | Кандидатов | Подтверждено | Снято |
| C-01 | 0 | 0 | — |
Доля FR/NFR, прошедших механику EARS: NN % (X из Y).
Трассируемость: BR без требований — n; без компонента — n; без модуля — n; без change — n; в двух changes — n; FR из CH-00–CH-02 без задач — n; задачи без FR — n.

## 3. Сквозные прогоны
| Сценарий | Шагов | Определено | Не определено | Находки |

## 4. Находки
| ID | Уровень | Документ / раздел | Что не так (цитата) | Почему важно | Что сделать | Куда возвращаться |

## 5. Условия (для READY WITH CONDITIONS)
| Условие | До какого change должно быть закрыто | Кто |

## 6. Проверка EARS — детали
| FR | Проблема | Предложенная формулировка |

## 7. Что проверено и признано хорошим
Коротко, с числами: что посчитано машиной и сошлось, какие прогоны прошли без пробелов.
```

## После отчёта

1. Запиши отчёт, обнови `docs/STATUS.md` (строка `audit`: вердикт и дата).
2. Покажи вердикт и 3–5 самых важных находок в чате. Если находки — хвосты предыдущего круга правок, скажи это прямо и назови долю: это единственный способ заметить, что ломается процесс, а не документы.
3. Если есть Minor — `AskUserQuestion`: «Исправить Minor сейчас» / «Показать список правок до применения» / «Не трогать». При согласии правь точечно (`Edit`, не перезапись), поднимай версию, добавляй строку в журнал изменений, помечай находку в отчёте как `fixed`. Blocker и Major не правь без отдельного решения пользователя: покажи, какой шаг перезапустить.
4. **После каждого блока правок — три прохода, а не один.** Повторный прогон батареи (`audit_checks.py`) обязателен, но его мало: она видит структуру, а не предмет.

   **По идентификаторам.** Для каждого изменённого ID, имени поля, ключа и значения словаря — `grep` по всем документам: каждое упоминание всё ещё верно. Разбил требование — проверь ссылки на старый ID; изменил приоритет — прогони C-09; изменил состав контракта — C-06 и C-12.

   **По предмету решения — обязателен для каждого нового требования.** Новое требование опаснее исправленной формулировки: оно заводит второго носителя решения, а первый остаётся на месте и продолжает говорить своё. Поиск по ID его не найдёт — старый текст нового ID не содержит. Ищи не ID, а предмет: имя поля и его значения, имя функции, которая это решение исполняет, слово из триггера, номер события, название этапа. Завёл «`stage` маркера `applied` равен `tests`» — грепни `toApplied`, `applied`, `stage` по дизайну. Завёл носителя события — грепни номер события и соседние. Завёл порядок правил — грепни имя функции и прозу алгоритма, где тот же порядок описан словами.

   **По потребителям.** Для каждого нового требования назови документ, по которому будут писать код, и проверь, что там записано то же самое. Требование, добавленное только в требования, — половина работы: у него должен появиться носитель в архитектуре и дизайне и место в change плана изменений.

   Правило приёмки круга: ни одна находка следующего аудита не должна быть местом, которое ты правил на этом. Долю хвостов называй в отчёте числом — это единственная метрика, по которой видно, что ломается процесс, а не документы.
5. Обнови в шапке отчёта «Проверенные версии» и дату, статус `approved` у исправленных документов сохрани.
6. Если вердикт READY / READY WITH CONDITIONS — скажи, что следующий шаг `/kickoff`, и остановись. Не запускай его.

## Чего не делать

- Не считать требование заведённым, пока не названы три вещи: кто порождает его триггер, кто читает его результат, в каком документе живёт его носитель. Требование без входа — тот же блокер, что отсутствующее требование, только заметный кругом позже.
- Не считать зелёную батарею достаточной: она проверяет структуру, а не замысел. Без сквозных прогонов проход неполный.
- Не подавать кандидатов батареи как находки: каждая находка уровня Blocker и Major подтверждается цитатой.
