# Правила changes

OpenSpec — адаптер плана. Создавай и проверяй changes командами из docs/kickoff/adapter.json и инструкциями установленного CLI (например, instructions для артефакта, если CLI его поддерживает). Нет нужной команды или схема не выражает срез — блокер адаптера с необходимым действием, не обход через ручную структуру.

## Proposal

Каталог — `openspec/changes/<id>`, где id — ID среза плана. Proposal содержит:
- plan_hash, ID плана и среза;
- outcome и rationale среза, basis;
- обязательства среза с разделением: владелец реализации (owners) и носитель, который соблюдает и проверяет (applies_to);
- сценарии, контракты и задачи-источники DDD;
- depends_on и условия плана, относящиеся к change, с timing;
- что остаётся за пределами change: будущие сценарии coverage и срезы, которые их проверят.

## Spec delta

- Требования и сценарии сохраняют смысл, язык, модальность, исключения, единицы, лимиты и IDs источника. Если адаптер требует иной синтаксис, сохрани оригинальную формулировку и проверь эквивалентность.
- ADDED/MODIFIED/REMOVED/RENAMED выбирай по текущим openspec/specs и changes-зависимостям: изменять можно существующее требование или введённое change, от которого зависит текущий.
- Сквозное требование определяется один раз — в change владельца; остальные носители ссылаются на него и проверяют, без повторного ADDED того же требования.
- Частичная гарантия: delta отражает только достигнутый в change scope. Оставшееся обязательство и срок его проверки фиксируй в proposal и трассировке; расширяй гарантию последующими delta, не меняя исходное требование. Неспособность адаптера выразить такой scope — блокер, не повод объявить будущую гарантию выполненной.
- Capability — обоснованная группировка поведения, не автоматическое отображение CAP. Два change в одной capability сериализуются (общий файл спецификации при архивации), поэтому не объединяй несвязанное поведение в одну capability, но и не дроби связное ради ширины волны.
- Инфраструктурный срез без поведения требует основания в плане и поддерживаемого схемой представления; не выдумывай skip_specs.

## Design и tasks

Change создаётся, когда все его зависимости архивированы, поэтому design и tasks пишутся сразу по фактическому коду с их результатами. tasks.md обязателен; design.md необязателен в схеме OpenSpec, но нужен, если решение неочевидно из контрактов.

- Основа — утверждённые задачи и контракты DDD и текущий код. Каждая задача имеет основание и проверяемый результат.
- Строки requirements.coverage плана переноси в задачи проверки конкретного change по change, scope и requires. Интеграционный сценарий, назначенный позднему срезу, не копируй в ранний.
- Открытые before_start условия не мешают созданию, но change с ними не готов к старту реализации; отрази это в tasks и итоге запуска.
- Новые файлы, ресурсы или зависимости, выявленные при подготовке, добавляй в writes и edges roadmap; если они противоречат утверждённым волнам — divergence.

## Проверка change

1. Трассировка: каждое обязательство, сценарий и coverage-строка среза представлены в proposal/delta/tasks; лишних обязательств нет.
2. Смысл: сравни формулировки delta с источниками, а не только IDs.
3. validate из adapter.json на текущем состоянии; не ослабляй strict-проверку.
4. `scaffoldctl.py bind` — хеши proposal и spec delta для roadmap.

Прерванное создание (каталог есть, в roadmap change ещё planned) продолжай, только если proposal содержит текущий plan_hash и ID среза, а история Git показывает, что каталог создан scaffold; иначе blocked. Существующее не перезаписывай без сравнения. Активный и архивированный change не пересоздаётся.
