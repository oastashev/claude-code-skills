# Контроль качества генерации

## До генерации

Установи normative baseline: роли, scope, версии, действующие решения и явные замещения. Снимок источника сохраняет факты, но не назначает им нормативность. Разделяй требование, пример, риск, допущение, решение и доказательство.

Для пакета сформулируй: какое обязательство раскрывается, что нельзя изменить, какие варианты допустимы, какие вопросы блокируют именно эту работу. Неразрешённый вопрос не заполняй правдоподобным поведением. Можно ограничить пакет независимой частью, явно сохранив отложенное как question с due-stage; нельзя сузить итоговый stage-review, чтобы скрыть пробел.

## Критерии

Каждый критерий получает PASS, FAIL, UNKNOWN или разрешённый политикой NOT_APPLICABLE, точный scope, причину и ссылки на основания. Для fragment полнота относится к выбранному смысловому блоку плюс его влиянию; для stage-review — ко всему плану этапа.

| Ключ | До создания текста | Проверка кандидата |
|---|---|---|
| structure | Определи роль, обязательные раскрытия, форматы и ID | Состав соответствует scope и стадии; нет потерянных сущностей |
| baseline | Зафиксируй термины, нормативность, версии, приоритеты | Для контекста есть единственное действующее решение; перевод сохраняет модальность |
| atomicity | Раздели независимо наблюдаемые обязательства | Одно требование не скрывает разные исходы и приоритеты |
| completeness | Перечисли входы, выходы, режимы, отказы, исключения и границы | Всё необходимое раскрыто на текущем уровне детализации; пробелы не спрятаны в позднюю фазу |
| consistency | Передай автору инварианты и ограничения всех предков | Нет несовместимых требований в одном достижимом контексте; алгоритмы и примеры не противоречат норме |
| verifiability | Задай наблюдаемый исход и различающий сценарий | Есть правдоподобная неправильная реализация, которую сценарий отвергает; NFR имеют метрику и условия |
| feasibility | Выдели критические предпосылки механизма | Архитектура, ресурсы, квоты и платформенные ограничения совместимы с обещаниями |
| contracts | Определи словари, типы, единицы, defaults и права изменения | Согласованы required/optional, wire/internal, атомарность, ошибки, таймауты |
| traceability | Укажи основание и ожидаемый механизм выполнения | Вперёд выполнены обязательства, назад обоснованы решения; ссылка на ID не заменяет объяснение |
| external_assumptions | Раздели проверенный внешний контракт и допущение | Указаны версии/источники, границы доверия; непроверенное не названо фактом |

## Уровень детализации этапа

| Стадия | Обязательное содержание | Не требуй раньше времени |
|---|---|---|
| BRD | Цели, пользователи, бизнес-результаты, границы, исключения, ограничения, критерии успеха | Модули, API и выбор библиотек |
| TRD | FR/NFR, actor/trigger/precondition/action/outcome, exceptions/limits/phase/modality, данные, сценарии приёмки | Подробный код каждого алгоритма |
| SAD | Компоненты, ответственность за FR/NFR, границы, механизмы, ADR и существенные риски | Все поля внутренних типов |
| SDD | Модули, взаимодействия, состояния, контракты, ошибки и обязанности сторон | Детализацию ещё не заявленного будущего среза |
| DDD | Алгоритмы, схемы, интерфейсы, задачи, зависимости и фазы реализации в заявленном scope | Успешные runtime-тесты ещё не написанного кода |

Все документы читаются против действующих предков, а обратная правка — также против существующих потомков. Проектное решение может быть новым, если оно явно обосновано и не меняет бизнес-обязательство молча. Поиск основания только по соседнему документу недостаточен.

## Критический проход

Читай точный текст источников и нормативных записей, затем generated preview. Сначала сформулируй, что документ предписывает; не начинай с предположения, что автор прав. Сопоставь statement и data: наличие обоих полей не доказывает эквивалентность. Проверь, что пояснения, таблицы и заголовки не вводят дополнительных обязательств.

Для каждого ребра поясни, чем refines/implements/verifies выполняется по смыслу. Например, «модуль ссылается на FR» недостаточно; нужен механизм и его поведение в исключениях. Будущие связи помечай UNKNOWN либо NOT_APPLICABLE с due-stage. Отсутствующую ещё не созданную сущность не заменяй фиктивной реализацией: зафиксируй ожидаемое раскрытие в плане и question/assumption при необходимости.

Применяй только релевантные матрицы:

- Основной и резервный путь, online/offline/disabled, приоритет источников и исключения.
- Границы лимитов, повтор, расход предыдущей попытки, недоступная квота.
- Достижимость состояний, safety/liveness, одновременные условия, неизвестный исход timeout.
- Авария до/после устойчивого шага, потеря состояния, конкуренция, идемпотентность.
- Минимальный объект каждого статуса, enum, отсутствие поля, default, единицы и миграции.
- Сохранение содержимого при валидном формате; разные языковые формулировки одной нормы.
- Обязательства «с первого запуска», зависимости задач и defaults ещё не введённой функции.
- Наблюдаемость основного и fallback-пути, частичный результат и источник метрик.

Для кандидата дефекта: выпиши точные положения → установи общий достижимый контекст → проверь исключение/замещение → построй минимальный сценарий → покажи несовместимые или недоопределённые результаты. Пересмотри собственную находку на предмет пропущенного разрешающего решения.

## Находки и gates

- contradiction — несовместимые нормативные обязательства в одном контексте.
- contract_gap — разные наблюдаемые реализации удовлетворяют неполному контракту.
- hypothesis — риск, для подтверждения которого недостаточно оснований.
- missing_evidence — обязательная проверка не обеспечена материалом/результатом.

Severity и confidence различай. Critical/High/Medium contradiction или contract_gap блокируют принятие; Low остаётся замечанием. Обязательное missing_evidence даёт UNKNOWN. Риск, принятый пользователем, сохраняется с владельцем, scope и основанием; это не автоматическое исправление противоречия.

Состояния findings: open, resolved, retracted. Для resolved нужна проверка текущего исправления, для retracted — объяснение ошибочности прежнего вывода. Сохраняй стабильный ID при переносе между пакетами, цитаты/указатели источников, контрпример, последствие и условие закрытия. Список не должен обнуляться только потому, что пакет новый.

Документный gate отделён от formal и runtime. Скрипт объединяет только обязательные policy gates, но встроенный обнаруженный конфликт модели всегда блокирует. Необязательный UNKNOWN сохраняется в отчёте. Formal PASS относится к проверенным моделям и их доменам, не к полноте всего проекта. Runtime PASS требует записи выполненной команды, результата, снимка отчёта и хешей проверенных сущностей; реальность запуска проверяет исполнитель/ревьюер.

## Промпт критического прохода

«Проверь данный кандидат по исходным материалам и десяти критериям quality.md. Scope и stage указаны в контракте. Не переноси прежний PASS автоматически. Для каждого утверждения PASS укажи конкретный механизм/фрагмент и различающий пример. Проверь все ребра графа по смыслу и все обязательства стадии по плану покрытия. Раздели противоречия, пробелы, гипотезы и отсутствие доказательств. Не исправляй кандидат во время ревью: запиши findings и заполни review.json с исходной identity. Не объявляй написанный сценарий выполненным тестом. Если проверял автор, явно запиши это в reviewer; не заявляй независимость».
