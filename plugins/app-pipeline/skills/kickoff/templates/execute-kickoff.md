# Execute kickoff

Прочитай plan/baseline/review/approval/execution/adapter из docs/kickoff/, AGENTS.md и относящиеся к change источники и контракты. До изменения файлов:
`python docs/kickoff/tools/planctl.py check --root . --plan docs/kickoff/plan.json --execution`.
Ошибка или изменённое основание блокирует работу. Не редактируй спецификацию, CURRENT, approvals или audit. Новое продуктовое/архитектурное решение → assemble, audit и пересмотр плана.

## Выбор и возобновление

Один запуск реализует один change либо координирует интеграцию. Явное указание пользователя учитывай в рамках зависимостей.

1. Сопоставь **все** IDs плана с execution, активными/архивными артефактами и Git. Пропавший каталог не означает завершение. Несовпадение → остановка.
2. Режим берётся из фиксированной записи execution, ветки и worktree. Основной checkout координирует все назначенные worker-changes, включая последний. Число активных каталогов не переключает worker в sequential.
3. Старт разрешён после архивирования зависимостей и закрытия всех before_start условий change с evidence. Выбирай готовый по волне, затем ID. Нет готовых → сообщи блокеры. before_verify/before_release проверяются на своих барьерах.
4. Сверь git status с change, веткой и состоянием. Неизвестные изменения не присваивай себе, не stash/reset/delete. Потеря state одновременно с незавершённым деревом → безопасная остановка и ручное восстановление.
5. checkpoint читается из JSON, не по Markdown-маркеру. Проверь required_evidence, используй уже предоставленный ответ без повторного вопроса. Одно «готово» не заменяет необходимые данные.
6. verified действительно только для source_commit и контекста проверки. Изменение кода/specs/зависимостей или существенной среды возвращает verifying.

Состояние условий и evidence закрытия берутся из актуального центрального execution.conditions; состав/смысл/timing — из утверждённого плана. Worker передаёт свидетельство координатору, не переписывает plan или центральное состояние. Перед соответствующим барьером получи актуальное подтверждение закрытия. Изменить условие можно только через пересмотр плана.

## Подготовка, реализация, проверка

В preparing используй инструкции установленного CLI из adapter и текущий код для design/tasks, сохраняя утверждённые обязательства. Каждая задача имеет основание и результат. Сначала проверь смысл и трассировку, затем формат.

В implementing выполняй задачи внутри scope. Частичное не отмечай завершённым. Применимые сквозные ограничения обязательны. Коммить только собственные известные пути. Настройка worktree — по проектной инструкции, без автоматического копирования всех .env/доступов основного checkout.

В verifying проверь before_verify, scenario/checks, назначенные текущему change через requirements.coverage, и применимые контракты. Для каждого coverage.requires проверь готовность зависимостей; текущий change проверяется после своей реализации. Выполни реальные команды и назначенные локальные/интеграционные проверки. Не требуй ещё не наступившую проверку другого среза, но не объявляй всю гарантию подтверждённой до полного coverage. Сохрани source_commit, команды, версии/среду, exit_code, наблюдения и логи без секретов. Невыполненная обязательная текущая проверка — UNKNOWN/blocked; наличие теста и зелёный формат не доказывают сценарий. Для старого плана без coverage используй прежнее полное назначение сценариев каждому носителю.

Если нужен пользователь, запиши checkpoint={reason, required_evidence}, state=blocked, результаты и следующий шаг. Не вводи фиксированный лимит двух попыток для любой ошибки; останавливайся, когда исчерпано обоснованное локальное исправление или нужно новое решение.

## Интеграция

Worker не архивирует и не пишет центральный execution.json. Он сохраняет docs/kickoff/workers/<id>.json со state=verified, source_commit/evidence и передаёт координатору ветку/commit.

Координатор — единственный писатель центрального состояния. Перед изменением возьми эксклюзивный файловый lock docs/kickoff/coordinator.lock через создание с отказом при существовании; запиши идентификатор запуска. Существующий lock не удаляй по одному возрасту: проверь владельца, при неопределённости остановись. Освобождай только свой lock после сохранения состояния. Создавай worktree в пределах разрешённой волны и max_workers; существующая ветка требует проверки владельца и пути.

До merge: чистое интеграционное дерево, записанные integration HEAD/worker HEAD, проверенное evidence worker, зависимости и условия. Сохрани state=integrating и оба SHA **до** операции. Merge по одному change. Общие файлы не дают права выбирать обе стороны автоматически: проверь смысл конфликта или верни владельцу.

Запись integrating сначала закоммить отдельным известным путём execution.json; различай исходный integration SHA и SHA этого служебного коммита. Временный coordinator.lock исключён из Git. Снова проверь чистоту дерева перед merge: журнал не должен смешиваться с изменениями кода.

После merge повтори применимые сценарии и интеграционные проверки. Ошибка → остановка с сохранением состояния; автоматический reset --hard запрещён. Восстановление — по сохранённым SHA и фактическому дереву, без удаления неизвестной работы.

## Архив и завершение

Sequential change проходит те же проверки перед архивом, без worker handoff. Before_release обязательно перед выпуском; если archive является выпуском по проектной политике — до archive. Если выпуск отдельный, явно сохраняй release blocked до закрытия условий.

Архивируй проверенной командой CLI из adapter, проверь resulting specs/трассировку. Запиши archive path/commit и state=archived только после успешных операций. При прерывании merge/archive сначала сопоставь SHA, Git и каталоги; не повторяй вслепую.

Удаляй worktree/ветку только после подтверждения merge, сохранения evidence и проверки отсутствия незакоммиченных изменений, без force. Worker-запись сохраняется в истории. Если evidence коммитится после проверки, докажи, что diff после source_commit содержит только метаданные.

Завершение плана требует каждого ожидаемого change с архивом/evidence, исполнения всех строк coverage включённых обязательств, сквозного сценария полезного результата MVP на итоговом интеграционном commit и закрытия обязательных условий. Проверки на ранних commit не заменяют регрессионную/интеграционную проверку итогового кода. Различай «реализация завершена» и «выпуск разрешён». Пустой список активных changes не доказывает завершение.

Итог: change/состояние, фактические проверки, оставшиеся условия и следующий шаг. Не запускай следующий change автоматически, не пушь/развёртывай сверх ранее разрешённого scope.
