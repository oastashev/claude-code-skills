# Init kickoff

Инициализируй утверждённый план в существующем репозитории. Не реализуй приложение и не запускай execute автоматически.

1. Найди корень Git, прочитай docs/kickoff/plan.json, baseline.json, review.json, approval.json и docs/07-kickoff.md. Запусти `python docs/kickoff/tools/planctl.py check --root . --plan docs/kickoff/plan.json --execution`. Ошибка, UNKNOWN, неподтверждённая редакция или изменённый baseline блокируют запуск. Проверь фактическое происхождение approval и полноту baseline, не только JSON.
2. Зафиксируй git status, ветку и хеши затрагиваемых файлов. Не присваивай чужие изменения. Существующие AGENTS.md/конфигурацию прочитай; добавляй только согласованные правила. При конфликте покажи конкретное изменение. Не используй git add -A.
3. OpenSpec — адаптер плана. Проверь установленную версию, локальные --help, схему и инструкции CLI. Не устанавливай @latest автоматически и не используй неподтверждённые flags. Нет CLI/совместимости — блокер с необходимым действием. Запиши версию/схему в docs/kickoff/adapter.json; не ослабляй validation.
4. Инициализируй только реально используемые пользователем интеграции агентов. Сохрани существующие specs/changes; различай текущее поведение и будущие delta, не объявляй любой проект greenfield.
5. Создай changes строго по IDs/зависимостям/scope плана. Proposal содержит plan_hash, источники, ограничения, условия и результат. Требования и сценарии сохраняют смысл, язык, модальность, исключения и IDs. Для сквозного требования — определение и ссылки из применимых changes, без повторных ADDED одного требования. Порядок ADDED/MODIFIED сверяй с текущими specs и зависимостями. Capability — обоснованная группировка, не автоматическое отображение CAP.
6. design/tasks готовь для ближайших готовых срезов по утверждённым задачам/контрактам; остальные ещё не готовы к реализации. Валидируй по поддерживаемой CLI стадии. Не навязывай первые три changes. Инфраструктурный срез требует основания и поддерживаемого схемой представления; не выдумывай skip_specs.
7. В AGENTS.md отрази фактическую архитектуру, команды и правила источников. Не добавляй обязательные четыре слоя, язык требований, CI или линтер вопреки спецификации. Неизвестная команда — условие, а не выдумка.
8. Создай execution.json по форме ниже: ровно все IDs, state=planned, фиксированные mode/wave, интеграционная ветка, пустые evidence/archive/checkpoint. В parallel-плане срезы многоместной волны получают mode=worker навсегда, даже когда останется один. До создания branch/worktree=null. Одиночные волны могут иметь mode=sequential.
9. Скопируй docs/execute-kickoff.md в каталог скиллов выбранного агента (для Claude Code .claude/skills/execute-kickoff/SKILL.md). Существующий файл сверяй по происхождению. Не устанавливай незапрошенные интеграции.
10. Проверь трассировку всех IDs и сценариев, смысловую эквивалентность и validation CLI. Коммить только известные созданные/изменённые пути, не пушь. Повторный запуск сверяет plan_hash и дополняет отсутствующее без сброса выполнения.

Переноси requirements.coverage в задачи проверок конкретного change: сценарий назначается по change, scope и requires. Не копируй будущий интеграционный тест в ранний срез. Полная гарантия источника не считается реализованной после первого фрагмента: в delta/specs отражай только достигнутый scope, а оставшееся обязательство и срок проверки сохраняй в proposal и трассировке плана. Расширяй достигнутую гарантию последующими поддерживаемыми delta, не меняя исходное требование. Неспособность адаптера выразить такой scope — блокер, не повод объявить будущую гарантию выполненной.

Варианты из parallel-анализа — рекомендации. Создавай execution только по утверждённым execution.mode/max_workers и change.wave, не по самому широкому варианту отчёта. Каждая пара выбранной совместной волны должна иметь independent в parallelism.pairs и пройти check. Если при подготовке выявлен новый общий ресурс или зависимость, верни план на revise; не исправляй утверждённые волны молча.

execution.json:
{schema: 1, plan_hash, integration_branch, changes: {id: {mode, wave, branch, worktree, state, source_commit, evidence: [], checkpoint: null, archive: null}}, conditions: {id: {status, evidence}}}.
Начальные conditions копируй из плана. Их закрытие с evidence ведётся в execution, не правкой утверждённого plan. Смысл и timing условий не меняются без пересмотра. Добавь точное исключение docs/kickoff/coordinator.lock в .gitignore; сам execution и доказательства сохраняются в Git.
Состояния: planned/preparing/implementing/blocked/verifying/verified/integrating/archived.
Worker пишет docs/kickoff/workers/<id>.json; центральное состояние — только координатор.
adapter.json содержит версию CLI, схему, фактические команды проверки/архива и отображение ID плана → change/capability. Секреты не сохраняй.

Перенос проекта должен включать все пути baseline, включая outputs/audit, полный docs/specification и planctl.py. Старый STATUS.md не является источником разрешения.

Прерывание с неопознанными изменениями → остановка и описание восстановления; не удаляй их ради повторного запуска. Итог: готовность, ограничения, следующий вызов execute; не объявляй проверенным поведение ещё не созданного приложения.
