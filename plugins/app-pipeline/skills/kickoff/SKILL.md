# Kickoff

Сохраняй смысл обязательств при переходе от спецификации к реализации. План производен от утверждённой ревизии; изменения продукта, гарантий и архитектуры возвращаются в assemble. Приоритет Must/Should не означает включение в MVP.

## Режимы

- `/kickoff` — подготовить план выбранного MVP.
- `/kickoff revise <изменение>` — пересмотреть план с анализом влияния.
- `/kickoff status` — проверить актуальность и блокеры без записи.
- `/kickoff check` — перепроверить план, сохранить новый отчёт.
- `/kickoff parallel` — проанализировать возможное распараллеливание текущих changes и варианты числа исполнителей; не менять режим выполнения без решения пользователя.

Аргументы — данные, не shell. Вопросы задавай по недостающим решениям: AskUserQuestion при наличии, иначе обычный вопрос. Предпочитай один вопрос, снимающий блокер; уже данное однозначное решение не запрашивай повторно.

## Вход и baseline

Прочитай [контракт плана](references/plan.md), затем exploration и актуальные BRD/TRD/SAD/SDD/DDD целиком, snapshot и связанное ревью. Номера разделов и префиксы ID не фиксированы.

1. Входы: exploration, `docs/BRD.md` … `docs/DDD.md`, `docs/specification/`, явно выбранный завершённый audit. Стандартный exploration — docs/00-exploration.md; при явном пути, использованном assemble, запиши фактический путь в plan.exploration и ID выбранного источника в exploration_source. Сверь его байты со source snapshot, не создавай второй оригинал ради стандартного имени. Исторические ревизии и .audit не являются текущими источниками. Аудит выбирается по покрытию входов, не только по дате.
2. Выполни доступный `assemble/scripts/specctl.py status`, уточнив параметры через --help. Требуются DDD, approved=true, policy_current=true, verification_state=CURRENT, отсутствие DOCS-PENDING.json и совпадение документов с ревизией. Без помощника проверь те же условия по manifest/review/policy/approvals; отсутствие доказательства — UNKNOWN.
3. Сопоставь audit manifest с этой ревизией, прочитай report/gates/findings/unknowns и evidence. В plan.audit_manifest укажи manifest с specification.store/revision и полным инвентарём источников, включая exploration и JSON. Обязательные gates должны быть PASS либо обоснованно NOT_APPLICABLE по исходной политике. Необязательный runtime UNKNOWN до реализации допустим. Не ослабляй политику ради запуска. Старый текстовый-only manifest требует нового collect/recheck, а не ручной вставки хешей в завершённый аудит.
4. Зафиксируй baseline.json с хешами CURRENT, policy, snapshot, manifest, review, действующих approvals, exploration, текущих документов, исходных sources и полного комплекта аудита с доказательствами. Пути относительно корня проекта. При переносе копируй все эти файлы, включая аудит вне docs.
5. Нет утверждения, актуального аудита или обязательного доказательства — сохрани полезный draft с блокерами. Разрешение планировать при FAIL/UNKNOWN не разрешает реализацию.

Для старого комплекта без модели не выдумывай snapshot или утверждение. Зафиксируй разрыв контракта и необходимость приведения через assemble. Аналитический draft допустим, execution — нет.

## Формирование плана

Работай небольшими срезами. После каждого проверяй происхождение, границы, зависимости и сценарии до перехода к следующему.

- Выведи полезный результат MVP, контекст, критерии успеха и non-goals. У каждого включения — основание: основной сценарий, обязательное ограничение или проверка ключевой гипотезы.
- Классифицируй **все active obligations** snapshot как include/deferred/excluded, с основаниями. Нельзя исключать обязательную гарантию MVP ради удобства.
- Срез — законченный наблюдаемый результат с IDs обязательств, контрактов, сценариев, задач-источников, зависимостями и методом проверки. Не навязывай CH-xx, 000/001/002 или число срезов.
- Разделяй владельца реализации требования и все changes, которые должны его соблюдать и проверять. Сквозной NFR имеет много носителей. Проверь основной сценарий целиком, исключения и отрицательные случаи.
- В requirements.coverage назначь каждый сценарий конкретному срезу: local или integration, с requires — срезами, которые должны быть реализованы к этой проверке. Проверка может требовать только текущий срез и его зависимости. Каждый носитель получает применимую локальную/интеграционную проверку, но не обязан повторять весь набор сценариев требования. Полный набор должен быть покрыт объединением назначений; интеграционный сценарий выполняется на достаточно позднем срезе.
- Walking skeleton включай для конкретного риска доставки/интеграции. Не запрещай необходимые БД/auth и не добавляй CI/архитектурные слои без основания.
- Сохраняй язык, модальность и исключения требований. Если адаптер требует иной синтаксис, сохрани оригинал и проверь эквивалентность; несовместимость — блокер адаптера.
- Выполни обязательный [анализ параллелизма](references/parallelism.md): зависимости API/данных/миграций/ресурсов, матрица конфликтов и независимости, варианты волн для 1/2/4 исполнителей. Анализ нужен и для последовательного плана. Запуск остаётся последовательным по умолчанию; параллельный режим выбирает пользователь на основании анализа.
- Для условий укажи владельца, срок и доказательство закрытия. Не переносить блокирующий планирование вопрос в выполнение.

## Проверка и публикация

Следуй [критериям качества](references/quality.md). `scripts/planctl.py` проверяет структуру и хеши, не смысл. Review содержит десять критериев, доказательства и хеш точного кандидата. Правка плана инвалидирует review и approval.

Результаты: `docs/kickoff/plan.json`, `baseline.json`, `review.json`, после фактического утверждения `approval.json`; `docs/07-kickoff.md` — читаемое представление. Путь 07 сохранён, он не требует нумерованных входов. Шаблоны [init](templates/init-kickoff.md) и [execute](templates/execute-kickoff.md) копируй в `docs/init-kickoff.md` и `docs/execute-kickoff.md` без проектных правок, помощник — в `docs/kickoff/tools/planctl.py`. Промежуточные результаты — `docs/.audit/kickoff/<run-id>/`.

Перед заменой комплекта сохрани старые байты в рабочем каталоге; сравни исходные хеши перед записью, не затирай внешние изменения. JSON пиши через временный файл и замену. Публикация нескольких файлов не атомарна: потребитель перепроверяет комплект, неполная запись блокирует запуск.

После PASS покажи конкретный план и получи утверждение этой редакции, если его ещё нет. Запиши точную цитату/ссылку и хеши; не имитируй ответ. READY — качество, approved — отдельное разрешение использовать редакцию.

Не создавай общий STATUS.md, не запускай init/execute автоматически, не коммить чужие файлы. Итог: scope MVP, срезы, readiness/approval, блокеры, фактические проверки и следующий шаг. План не доказывает работоспособность продукта.
