# Протокол анализа

## 1. Источники и нормализация

Создай карту: exploration/исходный дизайн/решения → BRD → TRD → SAD → SDD → DDD → модель, тесты и реализация. Это типовая последовательность; сохрани реальные роли проекта. Для каждого файла зафиксируй SHA-256, версию, статус, нормативность, точную область и заменённые положения. Исторический снимок полезен для происхождения, но не заменяет утверждённое решение. Дата файла и слово approved сами по себе не разрешают противоречивый baseline.

Различай цитируемый пример с FR-001 и нормативное определение FR-001. ID имеет namespace проекта/подсистемы. Диапазоны FR-001…FR-010, FR-001–010 разворачивай; не обрезай поиск статическими номерами строк. Таблица BR→FR с первым столбцом BR — ссылка, не повторное определение бизнес-требования. Кандидатов определений, найденных парсером, классифицируй вручную.

Нормализованное обязательство:

`source + scope/phase + modality + actor + trigger + precondition + action + observable outcome + exceptions + limits/units + precedence + acceptance evidence`.

Разделяй: требование, архитектурное решение, допущение, риск, пример, тестовый сценарий и результат теста. Составной BR может быть контейнером; его части должны иметь покрытие, но сам факт составности не всегда дефект. Перевод ru/en сравнивай по смыслу и модальности, а не по сходству слов.

На стыке explore → assemble отдельно проверь MVP / после MVP / non-goals: обсуждённая будущая идея не должна превращаться в обещание или задачи реализации без решения. Отличай stage документации от phase поставки. При наличии модели assemble связывай аудит с её ревизией/политикой и полным manifest по outputs.md. Исправляй generated-спецификацию только по repairs.md через новый пакет; повторное хеширование вручную изменённых Markdown не делает модель согласованной.

## 2. Десять критериев для каждого документа

| Критерий | Проверка и достаточное основание |
|---|---|
| Структура | Роль документа, необходимые по scope разделы, идентификаторы, версия, родительские ссылки; отсутствующий шаблон проекта не выдумывать. |
| Однозначность и baseline | Единственное действующее решение для заданного контекста; определены термины, численные границы, must/should, исключения, версия родителя. |
| Атомарность | Обязательства отдельно проверяемы; составное требование не скрывает независимые исходы и конфликтующий приоритет. |
| Полнота | Входы, выходы, happy path, ошибки, пределы, восстановление, режимы и исключения покрыты в рамках данного этапа. |
| Непротиворечивость | Нет двух несовместимых обязательств при одинаковых условиях, включая внутридокументные таблицы/примеры/алгоритмы. |
| Проверяемость | Есть наблюдаемый исход, условия, метрика/порог, метод и свидетельство; сценарий отличает корректную реализацию от правдоподобной ошибочной. |
| Реализуемость | Ограничения платформы, зависимости, производительность, ресурсы, квоты и объём работ совместимы; непроверенные предположения обозначены. |
| Термины и контракты | Единицы, enum, required/optional, defaults, wire/internal формы, схемы, права изменения, атомарность и таймауты согласованы. |
| Трассировка | Вперёд покрыты все обязательства; назад каждое техническое решение имеет основание или явное локальное решение; наличие ID не доказывает выполнение смысла. |
| Внешние предположения | Контракты CLI/API/библиотек и платформ имеют версию и доступное доказательство; источник/фикстура/реальный прогон различаются. |

Каждая ячейка содержит PASS, FAIL, UNKNOWN или NOT_APPLICABLE, scope и обоснование. Отсутствующий downstream в stage-mode — вне области, а отсутствующий обязательный родитель — UNKNOWN для зависимых проверок. Формулировка «всё проверено» недопустима при выборочном чтении.

## 3. Контрольные точки

| Переход | Смысловая проверка |
|---|---|
| Источники → BRD | Цели, CAP/US, ограничения и исключения не потеряны; решения не расширены без основания. |
| BRD → TRD | Каждый бизнес-результат имеет функциональные/NFR обязательства; технические fallback/defaults не обходят бизнес-ограничения. |
| TRD → SAD | Компоненты и ADR способны обеспечить FR/NFR; архитектурные риски не отменяют нормативную гарантию молча. |
| SAD/TRD → SDD | Модули, границы, зависимости, последовательности и состояния реализуют архитектуру и приоритеты требований. |
| SDD/TRD → DDD | Типы, алгоритмы, схемы, задачи и фазы согласованы; линтер/правила архитектуры не запрещают собственный дизайн. |
| Сквозной | Цель достигается в реальном end-to-end сценарии; все альтернативные пути и промежуточные фазы соблюдают обязательства. |

Граф: source→requirement→component→module→change/task→test/evidence. Храни тип ребра: derives/refines/implements/verifies/supersedes/conflicts. Для каждого ребра укажи syntactic, semantic-confirmed либо unknown. Отличай неподтверждённое происхождение от обоснованного нового технического требования. Не требуй искусственных ID там, где проект использует ссылки на разделы: используй локальные audit-ID, не переписывая документы.

## 4. Сквозные матрицы и контрпримеры

Применяй релевантные темы; отметь неприменимые, не придумывай продукту демоны, подписки или git.

- **Режимы и исключения:** основной/резервный путь, online/offline, включено/выключено/none, источник аутентификации и приоритет при двух источниках; границы оплаты и добровольного выбора.
- **Лимиты и повторы:** проверка перед каждой новой попыткой; расход предыдущей учтён один раз; изменение квоты между попытками; недоступный источник квоты; граница `<`/`<=`; лимит запусков и повторов может иметь разные определения.
- **Состояния:** достижимость, инварианты и запрещённые переходы; приоритет одновременно истинных условий; liveness без обхода safety; timeout — отказ, отмена или неизвестный исход?
- **Аварии и конкуренция:** остановка до/после каждого устойчивого шага, потеря/порча состояния, грязные данные, переживший родителя процесс, stale lock, параллельные запросы, идемпотентный повтор. Не объявляй crash-safe алгоритм доказанным без достаточной модели/кода.
- **Контракты данных:** минимальный валидный объект каждого статуса, пропущенные обязательные поля, неизвестный enum, default, нормализация wire/internal, timestamp/единицы, миграции. «Опционально в типе» и «всегда обязательно при записи» должны иметь явное объяснение.
- **Содержимое против формы:** прежнее тело требования с тем же заголовком; изменение числа/условия/сценария; валидный формат при неверном результате. Для переноса сравнивай с неизменными входами, не с изменённым результатом агента.
- **Кодировка и сохранность:** валидный символ U+FFFD не равен ошибке UTF-8; проверяется исходная последовательность байтов. «Меняется только checkbox» может конфликтовать с обязательной пометкой. Чётко разделяй разрешённую нормализацию и потерю данных.
- **Фазы:** обязательство «с первого запуска» должно иметь реализующий срез не позже первого использования; default ещё не введённой функции должен быть явным. Поздний подробный DDD не требуй раньше его заявленной фазы.
- **Наблюдаемость:** фактический исход команд, успех/отказ/частичный результат; журнал, ротации и fallback входят в определённый источник метрики; наличие события в запасном журнале не называй потерей, но проверь его учёт.
- **Установка и изоляция:** инструкция обновления согласована с независимостью установленной копии; пример команды и нормативная процедура не конфликтуют. Не запускай реальную установку ради проверки текста.

Для кандидата: (1) выпиши утверждения; (2) найди общий контекст; (3) проверь исключения и замещение; (4) построй минимальный сценарий; (5) покажи несовместимые результаты; (6) определи границы доказательства. Это отдельный критический проход по своим находкам, а не повторение первого вывода.

## 5. Доказательства и классификация

- `contradiction`: два нормативных утверждения одновременно невыполнимы в достижимом контексте.
- `contract_gap`: существенный контракт допускает разные наблюдаемые исходы; конкретная ошибка реализации не доказана.
- `hypothesis`: правдоподобный риск, которому не хватает доказательств; не входит в число подтверждённых дефектов.
- `missing_evidence`: нет необходимого материала/доступа/результата; отдельный U-реестр.

Уровни доказательства: `document`, `executed_counterexample`, `model`, `implementation_test`, `external_primary_source`. Записывай, что именно доказано каждым. Strict UTF-8 пример подтверждает ошибочность предиката из текста, но не баг неизвестной реализации.

Severity: Critical — доказанная угроза существенной необратимой потери/нарушения основного ограничения; High — существенная бизнес-гарантия, расход, восстановление или корректность результата; Medium — контракт/детализация/проверяемость; Low — редакционная ошибка без изменения поведения. Confidence оценивай отдельно от severity. Если есть несколько допустимых решений, предложи варианты; не выбирай новое бизнес-поведение под видом редакторской правки.

Default gate policy: документный FAIL при открытом подтверждённом нормативном расхождении/пробеле Critical/High/Medium; Low отражается как замечание. Непроверенный обязательный критерий даёт UNKNOWN, если нет основания FAIL. PASS возможен, только когда все обязательные проверки выбранного scope пройдены. NOT_APPLICABLE — вне scope с объяснением. Проектная политика имеет приоритет, её фиксируют в отчёте. Принятый риск не исчезает: решение/владелец/scope/срок исключения видны отдельно, без подмены базового результата проверки.

Формальный и runtime gate оцениваются независимо. Общий gate равен FAIL при FAIL обязательного gate, UNKNOWN при отсутствии FAIL и наличии обязательного UNKNOWN, иначе PASS. Необязательные для данного этапа проверки не блокируют его, но не превращаются в PASS.

## 6. Повторный аудит

Сопоставляй находки по устойчивому смыслу, затронутым ID и контексту, а не по строке/названию/хешу. Сохраняй прежние F/U-ID; новым назначай следующий свободный ID. Для каждой старой находки: confirmed, revised, resolved, retracted или unknown. Различай изменение фактов и изменение интерпретации.

Проверь весь граф зависимостей изменённых требований, включая предыдущие PASS. Если файлы не менялись, но добавлен более ранний источник, заново оцени происхождение и область исключений. «Режим был предусмотрен» снимает обвинение в самовольном расширении, но не обязательно конфликт с BRD. Удалённый из пакета документ не доказывает устранение его обязательств.

Снятие U-находки о доступности файла не означает исправление F-находок. Итоговая статистика отдельно показывает подтверждённые расхождения, пробелы, гипотезы, неизвестное, закрытые и пересмотренные находки. Старые отчёты остаются привязаны к своим хешам.
