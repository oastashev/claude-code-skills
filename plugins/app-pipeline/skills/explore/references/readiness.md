# Проверка передачи exploration в assemble

Проверяй исходные материалы и текущую редакцию. Сохранённый текст, выбранный стек и согласие с одной рекомендацией не доказывают готовность всего exploration. Оцени уровень, достаточный для BRD, не требуя будущего детального дизайна.

## Контрольные вопросы

| Проверка | Достаточное основание |
|---|---|
| Проблема и пользователь | Понятно, кому и в какой ситуации нужен результат; утверждения о пользователях имеют источник либо помечены как допущения |
| Ценность и успех | Назван наблюдаемый полезный результат и способ оценить успех первой версии; метрики не выдуманы |
| Направление | Вариант выбран пользователем или ранее действующим решением; условия выбора и предварительность технологий явны |
| Согласованность | Цели, направление, ограничения, MVP и исключения совместимы; найденные конфликты разрешены явным решением |
| Минимальность MVP | Каждая включённая возможность имеет основание; проверена возможность отложить/упростить; нет необоснованного «на будущее» |
| Замкнутость MVP | Основной сценарий заканчивается полезным результатом; необходимые зависимости и гарантии не спрятаны после MVP |
| Сценарии и границы | Есть условия, действия, наблюдаемый результат, важные исключения и способ отличить ложный успех; глубина соответствует исследованию |
| Происхождение | Факты, решения, предложения, допущения и вопросы различимы; есть источники, устойчивые ID и записи подтверждений |
| Неизвестное | Для существенных A/Q понятны влияние, владелец, срок/стадия и зависимая работа; отложенный вопрос не нужен раньше указанной стадии |
| Передача | Документ самодостаточен для начала BRD; указаны готовность, утверждение, изменения и влияние на созданных потомков |

Запиши по каждой применимой проверке PASS, FAIL или UNKNOWN, со ссылками на разделы/ID и кратким обоснованием. Для действительно неприменимой проверки допустим NOT_APPLICABLE с причиной; основной результат, границы MVP и происхождение не могут стать неприменимыми только ради завершения этапа.

## Готовность и утверждение

- READY: выполнены обязательные проверки текущего scope; нет вопросов или неподтверждённых предпосылок, без которых нельзя начать BRD. Дальнейшие технические вопросы имеют корректные сроки разрешения.
- NOT_READY: установлен конкретный блокер — направление не выбрано, границы противоречат ограничениям, не определён необходимый исход, не замкнут MVP и т. п. Укажи требуемое решение или действие.
- UNKNOWN: не хватает доступных источников/результата исследования, чтобы оценить обязательный критерий. Укажи, какое доказательство нужно. При одновременном известном блокере используй NOT_READY, сохранив UNKNOWN-пункты.

Пользовательское утверждение независимо: draft/approved относится к конкретной редакции. Возможны draft + READY (ждём подтверждения), draft + NOT_READY (продолжаем), approved + UNKNOWN (пользователь утвердил снимок с явно указанными ограничениями). Последнее не разрешает начинать BRD до снятия UNKNOWN. Переход требует READY и явного утверждения редакции; одно не выводится из другого.

Техническое предположение можно оставить открытым до SAD, если оно не определяет возможность обещанного результата. Если от доступности внешнего API зависит весь выбранный продукт, отсутствие подтверждения может блокировать уже выбор направления. Решение определяется влиянием, а не названием категории вопроса.

При повторной оценке прочитай старые блокеры. Закрытие — ответ/проверка текущего основания; удаление строки или переименование вопроса не означает решения. Сохраняй отвергнутые и замещённые варианты в истории, если они объясняют текущие границы.

Для передачи в assemble отличай обсуждённую возможность после MVP от утверждённого обязательства будущего релиза. Первое не требует downstream-задач реализации. Сохрани ID и решение об откладывании/исключении, чтобы assemble мог проверить разбиение scope без нового обещания.

## Сценарии проверки самого скила

Эти случаи используются при ревью инструкций или отдельном разрешённом испытании; это не готовые требования проекта и не доказательство фактического поведения LLM.

| Входная ситуация | Ожидаемое поведение |
|---|---|
| Пользователь уже выбрал desktop и оффлайн | Сохранить выбор; проверить последствия, не требовать заново три платформы |
| После третьего вопроса неизвестно, разрешён ли сервер для персональных данных | Не прекращать выяснение по лимиту раундов; блокировать зависимый выбор, продолжать независимое |
| Во время обсуждения однопользовательского MVP возникает идея командных пространств | Показать новые роли/совместное владение/доступ, сохранить как предложение до решения |
| Пользователь явно просит включить командные пространства | Записать решение без повторного запроса согласия; уточнить только неясные последствия или конфликт бюджета |
| Экспорт — MVP, а получение обязательного результата требует отложенной интеграции | Найти незамкнутый путь; включить необходимую часть или изменить сценарий, не выставлять READY |
| Предлагается убрать обязательное сохранение данных ради скорости выпуска | Сохранить гарантию либо согласовать более узкий сценарий; не объявлять риск нормой MVP |
| Пользователь просит сохранить обсуждение без выбора направления | Записать draft, различить предложения, выставить NOT_READY и не запускать assemble |
| Не выбран движок БД, но бизнес-результат и ограничения ясны | Отложить вопрос до проектирования с владельцем и сроком; не требовать реализации сейчас |
| Пользователь подтвердил направление, но не финальный документ | Сохранить DEC, статус документа оставить draft |
| Изменён approved exploration при существующем DDD | Новая версия draft, история решения и влияние; не менять потомков и CURRENT автоматически |
