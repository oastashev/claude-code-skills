# Миграция пятистадийного комплекта

Режим `/specify migrate [путь к хранилищу v1]` переносит комплект формата v1 (стадии BRD, TRD, SAD, SDD, DDD, snapshot `schema: 1`) в новое хранилище v2 с профилем compact или extended. Смысл обязательств не меняется: переносятся те же сущности с теми же ID, меняются только стадии, композиция документов и место задач реализации. Хранилище v1 остаётся неизменной историей.

Миграция — не пакет изменения. Новые требования, правки exploration и исправление находок в неё не входят. Их делай отдельными пакетами `/specify change` после миграции, чтобы ревью переноса проверяло только перенос.

## Когда мигрировать

Сначала определи, где проект находится в цепочке, и покажи пользователю цену до начала работы:

| Состояние проекта | Рекомендация |
|---|---|
| v1 не дошёл до kickoff или план ещё не утверждён | Мигрировать: дальше kickoff работает только с v2 |
| Утверждённый план v1, materialize идёт или скоро начнётся | Не мигрировать до завершения плана: materialize выполняет план schema 1 и без миграции. Мигрировать перед следующим циклом изменений |
| Нужна правка спецификации посреди materialize | Мигрировать, затем новый audit и `/kickoff revise`. Архивированный change засчитывается новому плану по правилу roadmap.md: только если срез с тем же ID не изменился по смыслу |

Цена переноса: оценки рёбер из v1 не наследуются, потому что у нового хранилища нет проверенной базы. Каждое ребро оценивается заново, и каждая стадия заново утверждается пользователем. Перенос сокращает число утверждений (две или три стадии вместо пяти), но не отменяет их.

## 1. Инвентаризация v1 (только чтение)

Новый specctl формат v1 не читает. Проверь хранилище v1 сам, ничего в нём не меняя:

1. Прочитай `CURRENT`, `policy.json`, а также `manifest.json`, `snapshot.json` и `review.json` этой ревизии, approvals этой ревизии и опубликованные `docs/01-BRD.md` … `05-DDD.md`.
2. Сверь SHA-256 каждого файла ревизии с `manifest.files`, опубликованных документов — с хешами тех же имён, снимков `sources/<sha>.txt` — с их именами. Проверь, что `DOCS-PENDING.json` и `WRITE.lock` отсутствуют. Расхождение — остановка: сначала восстанови v1 его собственным протоколом (старая версия скила или Git), затем мигрируй.
3. Определи последнюю утверждённую стадию v1: approval с `revision` = CURRENT, совпадающим `snapshot_hash` и `policy_hash`. Неутверждённая последняя стадия переносится, но остаётся неутверждённой, пока пользователь не утвердит новую редакцию.
4. Незавершённые пакеты v1 в `.blueprint/specify/` не переносятся. Предложи пользователю сначала принять их старой версией скила или отказаться от них.
5. Сравни `docs/00-exploration.md` со снимком `SRC-EXPLORATION` из v1. Разница означает, что exploration изменился после v1; это учитывается в шаге 3.

Запиши инвентарь: ревизия, стадия и утверждения v1, количества сущностей по kind и stage, рёбер по type и due_stage, открытые findings. Он войдёт в отчёт миграции.

## 2. Решения до записи

Одной пачкой вопросов (AskUserQuestion) согласуй:

- **Профиль.** extended, если компоненты SAD — отдельные сервисы или deployable, у них разные команды или внешние границы, которые утверждаются отдельно от модулей. Иначе compact. Дай рекомендацию по фактическому содержимому SAD.
- **Архивирование v1.** По умолчанию: `git mv docs/specification docs/archive/specification-v1`, а опубликованные `docs/01-BRD.md` … `05-DDD.md` — через `git mv` в `docs/archive/specification-v1/published/`. Байты при переносе не меняются. Прежние kickoff-планы и аудиты, привязанные к старым путям, и так устаревают при миграции. Без Git — копирование с проверкой хешей, затем удаление оригиналов только после явного согласия. Альтернатива — оставить v1 на месте и создать v2 с другим `--root`; тогда этот путь придётся указывать kickoff и audit.
- **Политика gates.** Правила стадий объединяются: REQ = BRD + TRD, ARCH = SAD, DESIGN = SDD + DDD (+ SAD в compact). `formal_required` и `runtime_required` — true, если true хотя бы у одной исходной стадии; `na_allowed` — пересечение. Ослабление этого объединения требует явного решения пользователя.

Перемещение файлов проекта и выбор профиля — решения пользователя. Не выполняй их без ответа.

## 3. Новое хранилище и источники

```bash
python SKILL/scripts/specctl.py --root docs/specification init --profile compact
```

SKILL — фактический каталог скила specify, как в [workflow.md](workflow.md).

Затем приведи `policy.json` к согласованной политике до первого `prepare-review`.

Источники переносятся с теми же ID, потому что на них ссылаются `basis`:

- `SRC-EXPLORATION` создаёт `init` из текущего `docs/00-exploration.md`. Если exploration не менялся после v1, сущность совпадает по sha256 и basis переносятся как есть. Если менялся, импортируй прежний снимок как `SRC-EXPLORATION-V1` (`source --file <v1>/sources/<sha>.txt --id SRC-EXPLORATION-V1`) и замени в basis перенесённых сущностей `SRC-EXPLORATION` на `SRC-EXPLORATION-V1`. Новую редакцию exploration после миграции обработай отдельным `/specify change`.
- Каждый прочий source v1: `source --file <v1>/sources/<sha>.txt --id <тот же ID>`. Проверь, что выданный sha256 совпадает с v1. В кандидат вставь выданные `sha256` и `original`, а statement и остальные поля data возьми из сущности v1: они содержат классификацию нормативности.
- Импортируй как источники без нормативной силы: snapshot, review и approvals ревизии v1 (`SRC-V1-SNAPSHOT`, `SRC-V1-REVIEW`, `SRC-V1-APPROVALS`, для approvals — JSON-массив их содержимого в рабочем каталоге) и отчёт миграции из шага 7. Statement каждого: «исторический материал v1, не требование и не утверждение новой ревизии».

## 4. Правила отображения

| v1 | v2 |
|---|---|
| stage и due_stage BRD, TRD | REQ |
| stage и due_stage SAD | ARCH в extended, DESIGN в compact |
| stage и due_stage SDD, DDD | DESIGN |
| Активные сущности всех kind, кроме task | Переносятся с тем же ID, kind, status, statement, basis и data; меняется только stage |
| task | Не переносится: задачи и порядок работ строит kickoff. Содержание остаётся в `SRC-V1-SNAPSHOT` |
| Ребро, у которого конец — task | Не переносится |
| superseded-сущности и рёбра supersedes к ним | Не переносятся: история замещений остаётся в v1 и `SRC-V1-SNAPSHOT`. Если active-сущность ссылается на superseded в basis, остановись: v1 противоречит собственным правилам |
| Остальные рёбра | Переносятся с тем же ID, type, from, to и rationale; меняется только due_stage |
| evidence | Переносится, но targets хешируют сущность вместе со stage и потому устаревают. targets не переписывай; formal и runtime gates остаются UNKNOWN до повторного запуска проверки |

Для каждой задачи проверь, не держит ли её acceptance или outputs наблюдаемую гарантию, которой нет в obligation, scenario или contract. Такое содержание не подкладывай молча в модуль: это нормативный пробел v1. Запиши finding contract_gap с источником `SRC-V1-SNAPSHOT` и закрой его вопросом пользователю или отдельным пакетом после миграции. Prerequisites и фазы задач внеси в отчёт миграции как материал для kickoff, а не как требования.

После отображения вопрос с `blocking: true` может оказаться на текущей стадии (например, due SDD в extended становится DESIGN). Check его отвергнет: такой вопрос нужно разрешить до принятия, а не менять ему stage.

Документы собирай заново, сохраняя ID сущностей:

- **REQ:** разделы BRD, затем разделы TRD. Объединяй разделы, если они раскрывают одну capability. Совпадающие ID разделов переименуй префиксом (`brd-`, `trd-`).
- **ARCH (extended):** разделы SAD.
- **DESIGN:** разделы SDD, затем разделы DDD без задач; в compact сначала разделы SAD. Раздел, в котором были только задачи, не переносится.

Prose переносится дословно, кроме ссылок на удалённые задачи и названий документов (BRD → требования и т. п.). Каждое такое изменение отметь в отчёте. Новых нормативных фактов в prose нет, как и в обычном пакете.

## 5. Пакеты по стадиям

Стадия v2 перенесена целиком, если перенесены её исходные стадии v1: REQ — BRD и TRD; ARCH — SAD; DESIGN — SDD, а в compact также SAD. DDD для этого не нужен: задачи уходят в kickoff, остальное его содержание лишь уточняет проект. Целиком перенесённую стадию закрывай пакетом `mode: stage-review`. Частичную (v1 остановился на BRD) переноси пакетом `mode: fragment` и продолжай обычными пакетами `/specify` до stage-review. Если в compact v1 остановился на SAD, DESIGN без модулей не пройдёт check: перенеси REQ, а сущности SAD добавь в первый пакет DESIGN вместе с его модулями.

Для каждой стадии профиля, до которой дошёл v1, создай пакет:

1. `begin --stage REQ --contract <контракт>`. Цель контракта — «перенос стадий BRD, TRD из v1 <ревизия> без изменения смысла». scope — перенесённые ID. constraints — таблица отображения и запрет новых обязательств. outputs — документ стадии.
2. Добавь в candidate.json сущности и рёбра этой стадии и документ. Сущности следующих стадий добавляй в пакете их стадии.
3. `impact`, `check`, затем проверка переноса (шаг 6), затем `prepare-review`.
4. Ревью по quality.md и шардам, как у любого пакета этого режима, с двумя дополнениями. Открытые findings v1, относящиеся к этой стадии, внеси в review.json с прежними ID и пересмотри по существу. Reasons из review.json v1 не копируй: оценка свежая, v1 — только контекст.
5. `accept`. После stage-review покажи пользователю документ стадии, отчёт миграции этой стадии и отличия от v1. Утверждение v1 не переносится: для `approve` нужен фактический ответ пользователя об этой редакции. Ссылку на утверждение v1 можно привести как основание, но не как ответ.
6. Переходи к следующей стадии только после утверждения.

Миграция заканчивается на стадии v2, до которой дошёл v1. Дальше работа продолжается обычным `/specify stage`.

## 6. Проверка переноса

Перед каждым `prepare-review` выполни механическое сравнение с `SRC-V1-SNAPSHOT`. Для сравнения двух хранилищ у specctl нет команды, поэтому разовый скрипт в `.blueprint/specify/<run-id>/` допустим. Сохрани его вывод в отчёт.

- Каждая активная не-task сущность v1, срок которой наступил на этой стадии, есть в кандидате. Совпадают kind, status, statement, data и basis; расходятся только stage по таблице и basis в явно записанной замене на `SRC-EXPLORATION-V1`.
- Каждое ребро v1 без task и superseded-концов есть в кандидате с теми же полями, кроме due_stage.
- В кандидате нет сущностей и рёбер вне v1, кроме импортированных источников миграции.
- Перечень непереносимых элементов (task, их рёбра, superseded) совпадает с отчётом.

Сравнение подтверждает сохранность записей, но не смысл композиции документов и не отсутствие скрытых обязательств в задачах. Это остаётся ревью.

## 7. Отчёт миграции

`.blueprint/specify/<run-id>/migration.md`, импортированный как `SRC-MIGRATION` в пакет первой стадии:

- ревизия, стадии и утверждения v1; выбранный профиль и объединённая политика с основаниями;
- таблица «v1 stage → v2 stage» с количествами сущностей и рёбер;
- непереносимые элементы: задачи (ID, statement, prerequisites, фаза), их рёбра, superseded-сущности;
- найденные в задачах гарантии без носителя и созданные по ним findings;
- изменения prose и ID разделов;
- устаревшие evidence;
- результат проверки переноса по каждой стадии.

Если отчёт дополняется на следующих стадиях, импортируй новую редакцию под новым ID (`SRC-MIGRATION-DESIGN`): источник неизменяем.

## После миграции

- Зафиксируй в Git архив v1 и новое хранилище с документами отдельным коммитом, добавляя конкретные пути.
- Прежний audit и kickoff относятся к v1. Нужен новый полный `/audit` по новой CURRENT, затем `/kickoff` (или `/kickoff revise`, если materialize уже шёл) с планом schema 2.
- Отложенные правки — изменённый exploration, findings из задач, найденные при переносе дефекты — выполняй пакетами `/specify change`.
