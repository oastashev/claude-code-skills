# Формат спецификации v2

## Хранилище

```text
docs/00-exploration.md             # обязательный вход от /explore; не изменяется скилом
docs/01-requirements.md            # REQ: актуальные документы для чтения и аудита
docs/02-architecture.md            # ARCH: только профиль extended
docs/03-design.md                  # DESIGN
docs/specification/
  policy.json                     # version 2, profile, правила gates по стадиям профиля
  CURRENT                         # ID единственной опубликованной ревизии
  sources/<sha256>.txt             # неизменные снимки входов и отчётов
  revisions/<revision-id>/
    snapshot.json                 # нормативные записи и композиция документов
    review.json                   # фактические оценки именно этой ревизии
    manifest.json                 # родитель, хеши файлов, политика, контракт
    01-requirements.md ...        # исторические снимки документов данной ревизии
    RTM.md                        # производное представление графа
  approvals/<event-id>.json        # запись явного утверждения пользователя
  DOCS-PENDING.json                # только во время незавершённой публикации
.blueprint/specify/<run-id>/            # в корне проекта, вне docs/
  package.json                    # база CURRENT, целевая стадия, ID пакета, from (пакет-предшественник)
  contract.json
  candidate.json
  review-request.json             # идентичность входов и дайджесты источников наследования
  review.json                     # заполнение критического прохода
  review-brief.md                 # изменения, рёбра для оценки, открытые findings, список шардов
  preview/                        # производные документы для чтения до принятия
  shards/S-XX.json                # пакет чтения: рёбра UNKNOWN, их концы, соседние связи, основания
  shards/S-XX.result.json         # ответ ревьюера шарда по result_template
```

Пакет создаёт begin, исправленный — `begin --from <пакет>`. До prepare-review редактируются candidate.json и contract.json; после него заполняется review.json — командой `assess` из JSON-файлов оценок или правкой самого файла. Исправленный кандидат требует нового пакета и нового ревью. Нельзя редактировать package.json, review-request.json, опубликованные revisions и CURRENT вручную в обычном цикле.

Идентификаторы сущностей/рёбер/разделов: латинская буква, затем буквы/цифры/`_.-`, длина до 80. ID стабильны между ревизиями и имеют смысл в namespace хранилища. Дубли JSON-ключей запрещены. Даты UTC, формат JSON UTF-8; нечисловые NaN/Infinity запрещены.

## Snapshot

Корневые поля строго: `schema: 2`, `stage: REQ|ARCH|DESIGN`, `entities`, `edges`, `documents`. Последние три — объекты, индексируемые ID (documents — именем стадии). Все значения stage и due_stage принадлежат профилю policy.json: compact — REQ, DESIGN; extended — REQ, ARCH, DESIGN. Порядок стадий общий, профиль лишь исключает ARCH. Snapshot `schema: 1` (стадии BRD…DDD) не поддерживается.

Пример для ознакомления: [example-candidate.json](../assets/example-candidate.json). Его источник необходимо заменить реальным SRC-EXPLORATION из начальной ревизии, а учебные требования — обязательствами exploration. Пример не проходит проверку до этой замены и смыслового ревью. Не удаляй сущности, уже присутствующие в кандидате от begin.

### Entity

Общие обязательные поля:

| Поле | Значение |
|---|---|
| id | Совпадает с ключом в entities |
| kind | source, user_decision, obligation, term, contract, decision, behavior, scenario, component, module, question, assumption, evidence |
| stage | Стадия, к которой сущность должна быть раскрыта |
| status | active или superseded; candidate/accepted относятся к пакету/ревизии |
| statement | Человекочитаемая нормативная запись или описание типа сущности |
| basis | ID исходных оснований; пусто только у source; граф оснований без циклов |
| data | Структурированные свойства по типу |

statement и data описывают один смысл; при несовпадении нельзя молча выбрать победившее поле. Исправь кандидат, а совпадение проверь семантически. Общий реестр — место изменения; Markdown генерируется из него.

Источники `source` создаются командой source: data.sha256 указывает на снимок в sources; original хранит происхождение. Команда не добавляет сущность в snapshot — вставь выданный JSON с реальной классификацией statement. После принятия источник и user_decision нельзя переписать или удалить: добавь новую запись, явно объясни замещение.

Для `obligation` обязательны data.actor, trigger, precondition, action, outcome, exceptions, limits, phase, modality. actor/action/outcome/phase/modality — непустые строки; exceptions обычно массив, limits — объект с единицами и границами. Условия «нет» выражай явно, не подменяй неизвестное пустой строкой. Сценарий требуется уже на REQ на уровне наблюдаемого результата.

Для `scenario`: given, when, then, distinguishes. Последнее называет правдоподобную неправильную реализацию, которую сценарий отличает от корректной. Не добавляй executed=true сценарию: исполнение — отдельное evidence.

### Перенос границ exploration

`stage` — глубина раскрытия документации, `data.phase` — фаза поставки. Они не взаимозаменяемы: phase=after-MVP не отключает проверки active obligation на стадии DESIGN.

- MVP: подтверждённые гарантии преобразуй в obligations с фактической phase, основаниями и ссылками на G/C/CAP/US/DEC. Ссылки внутри exploration сохраняй в data.exploration_refs вместе с basis на source/решение; не создавай фиктивный ID сущности вместо ссылки на раздел.
- После MVP: обсуждённая возможность без обещания реализации остаётся в source; при необходимости отрази принятое решение об откладывании как decision/user_decision со scope и exploration_refs. Не создавай active obligation, component/module только ради будущей идеи. Предложение не становится user_decision без ответа пользователя.
- Non-goal: сохрани решение об исключении со scope и основаниями. Обязательный запрет для MVP может быть obligation; исключённая функция не получает компонента или модуля реализации.
- Явно обещанный будущий релиз: отдельное обязательство с phase и решением. Его добавление в проектируемый комплект расширяет scope документации и требует раскрытия; не объявляй его простой идеей «на потом». Если сейчас проектируется только MVP, сохрани будущий scope отдельно в источнике/решении и не включай в активный нормативный набор без согласованного расширения.

При stage-review сопоставь каждое включение/откладывание/исключение с моделью и проверь отсутствие новых обещаний. Не ослабляй структурные проверки и не меняй phase ради обхода недостающих компонентов или модулей.

Для остальных сущностей минимальные смысловые поля задаёт протокол (не все они проверяются скриптом):

| Тип | Рекомендуемые свойства data |
|---|---|
| user_decision | question, selected, rationale, user_message, superseded_scope |
| term | definition, unit, values, aliases |
| contract | participants, input, output, errors, defaults, invariants, ownership, atomicity |
| decision | problem, selected, alternatives, rationale, consequences, limitations |
| component/module | responsibility, provided_contracts, required_contracts, failure_behavior |
| assumption | claim, verification_method, owner, due, impact_if_false |
| question | question, options, blocking (bool), affected_scope; blocking=true на текущей стадии блокирует check |

Не заменяй конкретные поля общими словами «всё обработано». Для неприменимых контрактных свойств фиксируй причину. Новое техническое решение связывай с исходной потребностью и ограничениями; не требуй фиктивного FR для каждой детали.

### Behavior

Встроенно исполняются `data.representation: decision_table` и `state_machine` в проверяемой форме.

#### decision_table


```json
{
  "representation": "decision_table",
  "factors": {"empty": [true, false]},
  "slots": {"result": "required"},
  "rules": [{"when": {}, "effects": {"result": "valid-file"}}]
}
```

Домены — непустые уникальные массивы строк, целых чисел, bool или null. Значения сравниваются с учётом JSON-типа; true не равно 1. Слот required должен получить ровно один различимый исход; optional допускает отсутствие. Все совпавшие правила действуют одновременно: скрытого порядка и overrides нет. Приоритет вырази непересекающимися условиями. Максимум 100000 клеток до фильтрации; больший scope раздели обоснованно.

Если есть физически невозможные сочетания, разрешён явный непустой `allowed_cells` — список полных клеток из домена, плюс `exclusion_reason`. Скрипт проверяет принадлежность клеток, ревьюер — физическое обоснование исключений. Формулы и eval не поддерживаются. Пустая область не считается доказательством.

#### state_machine

```json
{
  "representation": "state_machine",
  "states": ["created", "running", "exited"],
  "initial": "created",
  "terminal": ["exited"],
  "events": ["start", "fail", "abort"],
  "guards": {"attempts": ["below-limit", "at-limit"]},
  "transitions": [
    {"from": "created", "on": "start", "to": "running"},
    {"from": "running", "on": "fail", "when": {"attempts": ["below-limit"]}, "to": "running", "effects": {"attempts": "+1"}},
    {"from": "running", "on": "fail", "when": {"attempts": ["at-limit"]}, "to": "exited"},
    {"from": ["created", "running"], "on": "abort", "to": "exited"}
  ],
  "ignored": [
    {"states": "created", "events": "fail", "reason": "До запуска нечему отказывать"},
    {"states": "running", "events": "start", "reason": "Повторный старт идемпотентен"}
  ]
}
```

- `states` и `events` — закрытые словари уникальных имён. `from`, `on`, `states`, `events` принимают одно имя или непустой список; `to` — ровно одно состояние. Составные записи вроде «a | b», «parked→queued» или «failing (прогон)» не являются именами: раздели их на состояния, события или guard.
- `terminal` — конечные состояния без исходящих переходов; пустой список означает циклический автомат (жизненный цикл демона, среды).
- `guards` — конечные домены, как factors таблицы решений. Условие счётчика или лимита выражай значением домена (`below-limit`, `at-limit`), а не формулой; `when` перечисляет допустимые значения, отсутствующий фактор означает любое значение.
- `effects` — необязательный объект скаляров; `note` — пояснение, не участвующее в проверке. Приоритета и порядка правил нет.
- `ignored` явно фиксирует, что событие в состоянии невозможно или не меняет состояния, с обязательной причиной; может ограничиваться `when`.

Скрипт перебирает все клетки «нетерминальное состояние × событие × сочетание guards» (не более 100000) и сообщает:

- CONFLICT — несколько переходов с разными `to`/`effects` или переход вместе с ignored;
- UNDEFINED — клетка не обработана и не проигнорирована явно;
- UNREACHABLE — состояние недостижимо из initial;
- TRAP — из достижимого состояния нельзя попасть в terminal, а для циклического автомата — вернуться в initial.

PASS означает детерминизм и полноту над объявленными словарями и эти графовые свойства. Он не доказывает, что события и guards соответствуют реальности, что автомат согласован с таблицами решений и обязательствами, и не учитывает справедливость и время: это остаётся ревью. Автомат без `events` считается записью в свободной форме: результат UNKNOWN, а поле `hints` указывает очевидные дефекты (имена вне states, состояния без выхода, недостижимые). Чтобы получить проверку, переведи автомат в форму выше.

Другие representation (например, sequence, resource_budget) хранятся как JSON и доступны семантическому ревью; встроенная машинная проверка возвращает UNKNOWN. Для формального PASS нужен подходящий внешний результат, либо все действующие behavior в поддерживаемой форме с успешной встроенной проверкой.

### Evidence

Внешний исполнимый результат — entity kind=evidence со ссылкой basis на импортированный source отчёта. Поля data:

- level: model или implementation_test;
- executed: true, command, exit_code: 0;
- targets: объект `{entity-id: SHA256(canonical(entity))}`;
- дополнительно version, environment, observed, scope — для интерпретации.

Хеш canonical: UTF-8 JSON с sort_keys=true, ensure_ascii=false, separators=(',', ':'), без NaN. Он связывает результат с проверенными сущностями. Добавление evidence в кандидат предшествует prepare-review. При изменении targets результат становится устаревшим; предыдущий evidence не переписывай, сохрани в истории и создай новый.

Поля executed и command являются утверждением исполнителя; скрипт проверяет структуру и привязки, но не доказывает факт внешнего запуска или достоверность сохранённого лога. Ревьюер обязан проверить реальный результат инструмента.

### Edge

`id`, `type`, `from`, `to`, `due_stage`, `rationale`. Оба конца должны существовать; неизвестные ID не заменяются заглушками. Направления:

- derives/refines: производная сущность → её основание;
- implements: компонент/модуль → реализуемое обязательство или контракт;
- verifies: сценарий → обязательство;
- depends_on: зависимая сущность → необходимое основание;
- supersedes: новое решение → заменяемое положение;
- conflicts: несовместимая сущность → другая; действующий конфликт в текущем scope блокирует принятие.

Синтаксическую целостность проверяет скрипт; допустимость типов концов и фактический смысл — ревьюер. У каждой действующей obligation текущей стадии должна быть verifies-связь от действующего scenario, доступного на этой стадии.

Начиная с ARCH (только extended) для каждого такого обязательства нужен структурный путь от component, с DESIGN — от module в обоих профилях. В compact компоненты допустимы на DESIGN, но путь от них не требуется. Задач (task) в модели нет: срезы и задачи реализации строят kickoff и materialize из модулей, контрактов и обязательств. Скрипт проходит basis и связи implements/refines/derives/depends_on, относящиеся к текущей стадии. Это проверка наличия пути, не доказательство реализации гарантии.

У каждого ребра есть отдельная оценка в review.edges. RTM показывает её, не выводит semantic-confirmed из наличия ID. Будущее due_stage не даёт права игнорировать уже действующее противоречие в самих обязательствах.

### Documents

documents содержит ровно стадии профиля от REQ до текущей. Документ: `title`, непустой `sections`. Раздел: `id`, `title`, `prose`, `entities: [ID]`. ID раздела уникален внутри документа. prose — пояснения; новые нормативные факты выноси в сущности. Все active-сущности, срок которых наступил, кроме source должны быть представлены хотя бы в одном документе.

Renderer показывает statement и структурированные поля сущностей в таблицах. Это простой проверяемый Markdown, не готовая полиграфическая вёрстка. Перекомпоновку выполняй в documents; редактирование производных .md не поддерживается как источник истины.

## Contract и review

Начальный контракт: [contract.json](../assets/contract.json). Он требует заполнения цели, scope, outputs и ограничений. mode=fragment — локальный шаг; mode=stage-review — финальная полнота этапа. unknowns содержит только блокирующее для пакета; перед prepare-review список должен быть пустым. Неблокирующие риски и будущие вопросы сохраняются как сущности, а не удаляются из истории.

prepare-review создаёт файл с identity, reviewer, criteria (десять ключей), edges (все рёбра), findings, formal и runtime. Оценка: `{status, reason, evidence: [ID]}`. Оценка ребра может дополнительно содержать `inherited: "package:<id>"|"revision:<id>"` и `context` (дайджест контекста при последней свежей оценке): её перенёс скрипт из проверенного ревью, потому что ребро и сущности обоих концов не изменились, а в stage-review — ещё и контекст ребра. check пересчитывает её по источнику, закреплённому в review-request; для новой оценки оба поля удаляют. Criteria, formal и runtime не наследуются. Рёбра с due_stage позже текущей стадии шаблон заполняет NOT_APPLICABLE. Допустимые ссылки evidence: ID сущности/ребра, имя документа, mechanical-report или путь к полю `<ID>#<путь>` — ключи через точку, индексы списков в скобках: `FR-006#data.exceptions[2]`, `E-12#rationale`, `BR-1#statement`. Путь должен существовать в кандидате; те же ссылки допустимы в sources находок. Точные поля указывай в evidence, а не цитатой в reason; reason объясняет, что доказано: механизм и различающий пример. Один ID без объяснения не является качественным ревью.

findings: уникальный стабильный id, kind, severity, state, reason, sources обязательны машинно; для contradiction/contract_gap также обязательны counterexample и closure. По протоколу сохраняй context, consequence и owner. Открытые находки прошлой принятой ревизии, а при `--from` весь реестр находок проверенного пакета-предшественника, переносятся в шаблон ревью; открытые должны быть явно пересмотрены, их удаление блокируется. Поля formal/runtime используют ту же форму оценки, но PASS требует подходящего исполнимого evidence. NOT_APPLICABLE допускается только политикой.

Внешний formal PASS должен покрывать все действующие behavior текущей стадии (если behavior нет — обязательства); runtime PASS — все действующие обязательства текущей стадии. Несколько evidence могут совместно покрывать набор. Узкий выполненный тест сохраняй как evidence с точным scope, оставляя gate UNKNOWN, если он не покрывает обязательный набор.

Политика по умолчанию требует все десять документных критериев; только external_assumptions может быть NOT_APPLICABLE с причиной. Formal/runtime необязательны до появления соответствующей необходимости. Перед генерацией зафиксируй обязательность по стадиям в policy.json; не ослабляй её ради прохождения проверки. Изменение policy инвалидирует ревью и текущие утверждения.
