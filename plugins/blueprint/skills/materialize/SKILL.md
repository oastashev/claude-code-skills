# Materialize

Переноси утверждённый план в changes по одному, без изменения его смысла. Срезы, границы, зависимости, волны и execution принадлежат плану kickoff; materialize переносит очередной срез в change, сверяет его с фактическим репозиторием и сообщает о расхождениях. Изменение раскладки — `/kickoff revise`, изменение продукта или архитектуры — specify и новый audit.

## Режимы

- `/materialize` — синхронизировать состояние и выполнить одно решение: create, wait, complete или blocked.
- `/materialize status` — показать решение, порядок и блокеры без записи.
- `/materialize parallel [N …]` — показать варианты волн оставшихся changes для указанного числа исполнителей (по умолчанию 1 2 4) без записи.

Аргументы — данные, не shell. Materialize работает без вопросов человеку: все продуктовые, архитектурные и плановые решения уже приняты в спецификации и утверждённом плане. Недостающее или неоднозначное решение — дефект входа, а не вопрос: зафиксируй его как blocked или divergence с источником и действием (`/kickoff revise`, либо specify и новый audit) и не выбирай вариант за человека.

## Решение запуска

Change завершён, когда архивирован в OpenSpec. Решение принимает `materializectl.py check` только по уточнённым зависимостям:

| next.action | Когда | Что делать |
|---|---|---|
| create | Есть не созданный change, все зависимости которого архивированы | Создать ровно этот change |
| wait | Каждый не созданный change зависит от неархивированных changes | Ничего не создавать; назвать активные changes (waiting_for) и незакрытые зависимости (pending) |
| complete | Все changes плана архивированы | Сообщить о завершении плана; проверка итогового MVP — вне materialize |
| blocked | Ошибки, divergence, устаревшее или не PASS ревью активного change | Ничего не создавать; перечислить причины и действия |

Из нескольких готовых выбирается первый по утверждённой волне и ID. Один запуск создаёт не больше одного change; следующий готовый создаёт следующий запуск. Накат changes — отдельный самодостаточный процесс: max_workers, execution и число уже активных changes на создание не влияют.

## Порядок работы

1. Работай в корне Git репозитория приложения после init-kickoff. Прочитай docs/kickoff/plan.json, baseline.json, review.json, approval.json, adapter.json, docs/07-kickoff.md, AGENTS.md, openspec/ (specs, changes, archive) и docs/materialize/.
2. Запусти `python docs/kickoff/tools/planctl.py check --root . --plan docs/kickoff/plan.json --execution`. Ненулевой код, отсутствие planctl.py или adapter.json — blocked с недостающим действием (перенос, init, kickoff).
3. Зафиксируй git status и ветку. Не присваивай чужие изменения. OpenSpec CLI используй в версии и с командами из adapter.json, сверяясь с локальным --help; расхождение — blocked, не установка @latest и не неподтверждённые flags.
4. Синхронизируй [roadmap](references/roadmap.md) с файловой системой: при первом запуске создай его со всеми changes в planned; changes, которые исполнитель архивировал, переведи в archived с путём архива и удали их пары. Ничего другого при синхронизации не меняй.
5. Выполни check и следуй next. Для create — создай change по [правилам changes](references/changes.md): proposal, spec delta, design, tasks по текущему коду, который уже содержит результаты зависимостей. Найденные при этом зависимости и общие ресурсы добавь в edges и writes, независимость от других активных changes оцени в pairs.
6. Проверь change командой validate из adapter.json, привяжи его через `materializectl.py bind`, переведи в active, запиши [ревью](references/roadmap.md) этого change и повтори check. Итог create считается готовым, только если повторный check вернул READY; иначе change остаётся созданным, а результат запуска — blocked с причинами.

Существующий каталог change, которого нет в roadmap как active, не перезаписывай и не присваивай: это blocked; в итоге укажи каталог, его происхождение по истории Git и plan_hash из proposal. Исключение — прерванное создание по [правилам changes](references/changes.md): доведи его до конца вместо нового решения.

## Порядок и параллелизм

- Зависимости плана сохраняются. Найденные в репозитории зависимости добавляются только с точными evidence.
- `materializectl.py` выводит зависимости из spec delta и конфликты общих capability и writes между активными changes. Смысловую независимость он не доказывает.
- Уточнение, противоречащее утверждённым волнам, — divergence: исполнитель опирается на план, поэтому не переставляй волны и не меняй execution.
- Варианты для 1/2/4 исполнителей — рекомендации для `/kickoff revise`. Для ещё не созданных changes они опираются на оценки плана, для активных — на оценки по репозиторию.

## Публикация

Результаты: `openspec/changes/<id>/`, `docs/materialize/roadmap.json`, `docs/materialize/reviews/<id>.json`, `docs/08-materialize.md` — читаемое представление. Вывод check сохраняй в `.blueprint/materialize/<run-id>/check.json`.

Перед заменой файла сравни его хеш с прочитанным, не затирай внешние изменения. JSON пиши через временный файл и замену. Коммить только известные созданные/изменённые пути, не пушь.

Не реализуй и не архивируй changes, не закрывай условия плана. Итог: решение запуска, созданный change или то, чего ждём, блокеры и условия, расхождения с планом, варианты параллелизма, фактические проверки и следующий шаг.
