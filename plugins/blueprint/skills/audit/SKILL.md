# Audit

Проведи документный аудит, отделяя доказанное противоречие от пробела контракта, гипотезы и отсутствующих доказательств. Проверяй исходные документы, а не только их резюме или прошлый отчёт. Отвечай на языке пользователя.

Запрос и параметры: $ARGUMENTS

## Режим и область

Понимай параметры как данные запроса, не как команду оболочки. Поддерживай:

- `/audit` — полный аудит доступного комплекта текущего проекта.
- `/audit stage DESIGN` — локальная проверка одного документа (здесь проекта), его согласованности со всеми доступными предками и уже существующими потомками. Будущие не созданные документы не считаются дефектом этапа.
- `/audit full docs/` — полный аудит указанного каталога.
- `/audit recheck --previous <каталог-аудита>` — повторный аудит с сохранением ID замечаний и сравнением входных хешей.

Пути и режим можно задать обычным текстом. Не требуй фиксированных имён файлов и не предполагай, что DDD обязательно означает Domain-Driven Design: установи роль документа по его содержимому. Если аргументов нет, обнаружь файлы через glob/rg, изучи оглавления и baseline. Прошлые отчёты, архивы и примеры отдели от текущих нормативных документов.

Аудит сам по себе не изменяет требования, код, версии или статус approved. Пиши только новые артефакты проверки. При явном запросе исправлений сначала подготовь доказанные находки, затем внеси авторизованные изменения и повтори затронутые проверки. Уже принятые пользователем решения используй без повторного вопроса. Вопрос нужен, если два несовместимых варианта поведения нельзя выбрать из источников; пока ожидаешь ответ, продолжай независимые проверки.

Перед исправлением прочитай [маршрут исправлений](references/repairs.md). Если документы созданы specify и существует specification/CURRENT, изменяй нормативную модель через новый пакет specify, а не опубликованный Markdown. Без исправленного и проверенного пакета находка не закрывается.

## Рабочая папка

Для временных файлов и промежуточных результатов используй `.blueprint/audit/` в корне проверяемого проекта, независимо от текущего каталога оболочки и расположения навыка. В начале запуска создай отдельный каталог `.blueprint/audit/<UTC-run-id>/`; при совпадении имени выбери новый ID, не перезаписывая прежний запуск.

Храни здесь конфигурацию входов, извлечённый текст, рабочие индексы, черновые реестры, результаты команд и контрпримеров. Порядок каталогов и команды — в [outputs.md](references/outputs.md). При обнаружении требований исключай `.blueprint/**`, включая итоговые отчёты в `.blueprint/outputs/`: это результаты анализа, а не новые исходные требования. Предыдущие результаты читай только как контекст recheck. Сохраняй промежуточные файлы после завершения для воспроизводимости; автоматическую очистку не выполняй. Итоговые отчёты размещай отдельно по шагу 8.

## Выполнение

1. **Зафиксируй входы.** Прочитай [protocol.md](references/protocol.md). Определи роли, версии, хеши, нормативность, порядок замещения, scope текущего этапа и доступность модели, кода, фикстур. Текущий текст с пометкой draft не становится approved от прохождения аудита. При неоднозначном baseline не выбирай молча самый новый файл.
2. **Собери структуру.** Создай конфигурацию по [outputs.md](references/outputs.md), затем вызови `scripts/audit_support.py collect`. Для текущего комплекта specify укажи specification.store и revision: помощник включает модель, политику, источники, утверждения и артефакты ревизии в manifest. Он хеширует все входы, проверяет синтаксис JSON, индексирует только Markdown/text; не выполняет код проекта и не доказывает понимание содержимого. Наличие байтов PDF/DOCX не означает, что файл прочитан: используй парсер с привязкой к оригиналу либо оставь соответствующий критерий UNKNOWN. Без Python выполни эквивалентную инвентаризацию и отрази ограничение.
3. **Прочитай и нормализуй обязательства.** Для каждого нормативного утверждения сохрани actor/trigger/precondition/action/result/exceptions/limits/phase/source. Раздели составные обязательства аналитически, не переписывая источник. Установи словари, единицы, границы, defaults, приоритеты и происхождение требований. Обработай весь заявленный scope; если пришлось использовать выборку, укажи её и оставь неохваченное UNKNOWN.
4. **Проверь этапы.** Для каждого документа цепочки (у specify: требования → архитектура в профиле extended → проект) заполни десять критериев protocol.md; для каждого доступного перехода выполни forward- и backward-трассировку. Проверяй все предки, не только соседний документ, и обратное влияние на уже существующих потомков. Отдельно оцени синтаксическое покрытие и смысловое выполнение обязательств.
5. **Проверь сквозные сценарии.** Выполни матрицы режимов, исключений, данных, состояний, фаз и отказов из protocol.md. Для каждого кандидата найди исключение/решение, которое могло его разрешить. Используй минимальный контрпример. Конкретные примеры из прежнего проекта — эвристики, не обязательные дефекты любого продукта.
6. **Проверь исполнимое, если оно доступно.** Изучи существующие скрипты и запусти уместные локальные проверки модели/схем/контрактов в пределах запроса. Запиши команду, версию, код выхода и результат. Пример сценария, текст `verified`, написанный тест и успешное рассуждение LLM не равны исполненному тесту. Не устанавливай внешние инструменты и не вызывай платные агенты только ради аудита без соответствующего разрешения.
7. **Пересмотри прежние выводы.** В recheck прочитай полный прошлый реестр, сравни все входы и проверь каждую открытую находку, а не только изменённые файлы. Новые исходники могут объяснить API/offline/optional-режим, не устранив конфликт с бизнес-требованиями. «Интерпретация уточнена» не означает «исправлено». Закрывай находку по текущему доказательству, не по исчезновению строки или файла.
8. **Выдай проверяемый результат.** Создай артефакты по outputs.md в новом каталоге `.blueprint/outputs/audit/<UTC-run-id>/` либо в указанном пользователем месте. Сверь цитаты с исходными байтами, стабильность хешей и суммарные количества. Перед финалом вызови `audit_support.py verify` для входного manifest. Если вход изменился в процессе, перепроверь зависимые выводы или отметь их STALE и gate UNKNOWN. Предыдущий аудит не перезаписывай.

## Правила выводов

- Не объявляй противоречием различие детализации, явное исключение, согласованный пересмотр или ещё не реализованный будущий срез.
- Для противоречия нужны несовместимые обязательства в одном достижимом контексте. Для пробела — конкретный недоопределённый контракт и различимые допустимые реализации. Риск без такого доказательства остаётся гипотезой.
- Отсутствующая модель/фикстура/код — UNKNOWN, а не PASS и не доказанный runtime-баг. Реестр непроверенного веди отдельно от дефектов.
- Не удаляй предусмотренные исходниками режимы ради формального совпадения текстов. Если бизнес изменил решение, должна существовать явная запись о замещении.
- Не объединяй документный, формальный и runtime gate в один необоснованный PASS. Для каждого назови scope, критерии блокировки и основания.
- Не делегируй работу автоматически. Если пользователь или проект явно разрешает независимый проверочный проход, дай проверяющему исходные документы без навязывания ожидаемых находок.

## Готовность результата

Для каждой подтверждённой находки есть точные источники, контекст, следствие, контрпример, минимальная рекомендация, владелец и условие закрытия. Каждая оценка PASS ограничена проверенным scope. Финальный ответ: итог gate, главные проблемы, что изменилось при recheck, что не проверено и ссылки на отчёт/реестр. Не выдавай план проверки вместо выполненного аудита.

Ресурсы: [протокол](references/protocol.md), [контракты артефактов и команды](references/outputs.md). Путь к помощнику относительно этой папки: `scripts/audit_support.py`. Он не привязан к текущему проекту или абсолютным путям.
