# Работа агентов в репозитории

## Назначение и карта

Это marketplace плагинов Claude Code, а не приложение, создаваемое этими
плагинами. Основной плагин `app-pipeline` проводит пользователя через
`explore → assemble → audit → kickoff → scaffold`.

- `.claude-plugin/marketplace.json` — каталог плагинов.
- `plugins/app-pipeline/.claude-plugin/plugin.json` — манифест плагина.
- `plugins/app-pipeline/skills/<name>/SKILL.md` — точка входа скила.
- `references/` — подробные правила; `assets/` — контракты и примеры.
- `scripts/` — Python CLI и тесты рядом с ними.
- `kickoff/templates/` — инструкции, переносимые в целевой проект.

Каталоги `docs/specification/`, `docs/kickoff/`, `docs/scaffold/` и `openspec/`, упоминаемые
скилами, относятся к целевым проектам. Не создавай их здесь и не запускай
пайплайн при обычном сопровождении marketplace.

## Перед изменениями

1. Прочитай `README.md` и проверь `git status --short`.
2. Прочитай изменяемый скил и относящиеся к задаче references, шаблоны,
   скрипты и тесты. Инструкции внутри скила описывают его выполнение
   пользователем; чтение для редактирования не означает запуск скила.
3. Сохраняй существующие изменения, включая untracked-файлы. Не делай
   reset, clean, stash или массовое форматирование ради чистого diff.
4. Выполняй задачу в пределах запроса. Не коммить, не публикуй и не меняй
   версии без соответствующей задачи пользователя.

## Правила изменений

- Сохраняй язык файла: инструкции скилов преимущественно на русском,
  README и идентификаторы — на английском. Текстовые файлы — UTF-8.
- Сохраняй YAML frontmatter `name` и `description` в `SKILL.md`.
  Ссылки на ресурсы делай относительными к содержащему их файлу.
- При изменении форматов, путей, CLI или статусов проверь все затронутые
  этапы: производитель данных, потребитель, references, assets, шаблоны
  и тесты должны описывать один контракт.
- Python-помощники рассчитаны на Python 3.10+ и стандартную библиотеку.
  Сохраняй автономность скилов: не добавляй runtime-зависимость от соседнего
  скила, сетевых сервисов или кода целевого проекта. Интеграционные тесты
  могут использовать соседние скилы.
- Не подменяй смысловую проверку машинной валидацией. Статус качества
  и утверждение пользователем — разные состояния. Не фабрикуй approvals,
  reviews и evidence; синтетические данные допустимы в явно обозначенных
  тестовых фикстурах.
- Сохраняй проверку актуальности хешей и защиту исходных документов при
  изменении операций записи. Тестовые артефакты создавай во временных папках.
- При добавлении плагина регистрируй фактический относительный путь
  `./plugins/<name>` в marketplace. При выпуске версии согласуй версии
  в marketplace и манифесте плагина, обнови описание в README.
- Не вводи новые инструменты сборки, линтеры или зависимости без
  необходимости для задачи; общего настроенного линтера здесь пока нет.

## Проверки

Команды выполняются из корня репозитория; требуется Python 3.10+.

```sh
python -m unittest discover -s plugins/app-pipeline/skills/assemble/scripts -p "test_*.py"
python -m unittest discover -s plugins/app-pipeline/skills/audit/scripts -p "test_*.py"
python -m unittest discover -s plugins/app-pipeline/skills/kickoff/scripts -p "test_*.py"
python -m unittest discover -s plugins/app-pipeline/skills/scaffold/scripts -p "test_*.py"
git diff --check
```

Запускай набор изменяемого помощника; при изменении межэтапного контракта —
все четыре. Набор kickoff включает интеграционные тесты цепочки и анализ
параллелизма. Discovery из корня не заменяет эти команды: папки скилов
не оформлены как Python-пакеты.

Для правок только Markdown проверь ссылки, соответствие реальным путям и
командам, а также diff. Для изменённых JSON проверь разбор через
`python -m json.tool <путь-к-файлу>` и согласованность контрактов.
Не добавляй тесты, которые лишь повторяют текст инструкций.

## Завершение

Проверь итоговый diff и статус. В ответе кратко укажи, что изменено,
какие проверки выполнены и какие ограничения остались. Если проверка
не запускалась или упала, сообщи об этом явно.
